# Автодеплой: пуш в `main` → обновление VPS

`.github/workflows/deploy.yml` при каждом пуше в `main` заходит на сервер по SSH
и запускает `deploy/deploy.sh`: `git merge --ff-only origin/main` и
`docker compose … up -d --build`. Запустить вручную — вкладка Actions → Deploy →
Run workflow.

Сборка идёт на самом сервере, как и при ручном деплое. Пока она идёт, сайт
может коротко недоступен.

## Одноразовая настройка

**1. Ключ только для деплоя** (на своей машине, без пароля):

```bash
ssh-keygen -t ed25519 -f virex-deploy -N "" -C "github-deploy"
```

Публичную часть — на сервер, в `~/.ssh/authorized_keys` того пользователя, под
которым лежит проект:

```bash
ssh-copy-id -i virex-deploy.pub USER@HOST
```

**2. Сервер:** в папке проекта должен быть `.env.prod`, `git pull` без пароля
(репозиторий публичный или стоит deploy key), пользователь входит в группу
`docker`. Для варианта A (Caddy) в `.env.prod` добавить строку
`COMPOSE_PROFILES=edge`. Скрипт запускается обычным `./deploy/deploy.sh`.

**3. Отпечаток сервера:**

```bash
ssh-keyscan -p 22 HOST
```

**4. Секреты** — GitHub → Settings → Secrets and variables → Actions:

| Секрет | Значение |
|---|---|
| `DEPLOY_HOST` | адрес сервера |
| `DEPLOY_USER` | пользователь SSH |
| `DEPLOY_PORT` | порт SSH (можно не задавать, по умолчанию 22) |
| `DEPLOY_DIR` | абсолютный путь к папке проекта на сервере |
| `DEPLOY_SSH_KEY` | содержимое приватного файла `virex-deploy` целиком |
| `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan` из шага 3 |

Приватный ключ после добавления в секрет удалить с локальной машины.

## Что деплой не делает

- **Не применяет ручные шаги выкладки.** Если в описании изменения сказано
  «требует ручного шага» (как в `user-activity-retention.md`), его нужно
  выполнить на сервере до или сразу после merge.
- **Схема БД** синхронизируется на старте `api` (`prisma db push`) и отказывается
  удалять колонки с данными. В этом случае `api` не поднимется, деплой покажет
  красный прогон, а данные останутся целы.
- **Не гоняет тесты.** Любой merge в `main` уходит на прод. Если нужен щит —
  включить в GitHub защиту ветки (обязательный PR) и добавить проверки.
- **Откат:** `git revert` плохого коммита и пуш в `main`, либо на сервере
  `git reset --hard <коммит>` и `docker compose … up -d --build` руками (после
  этого следующий деплой сольётся fast-forward'ом только при согласованной истории).
