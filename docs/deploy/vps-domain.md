# Домен и продакшен-запуск на VPS

Что делает эта инструкция: поднимает на VPS собранный стек продукта и заводит
на него домен, DNS которого живёт в Vercel. Без панели ISPmanager — домена не
будет на её вкладке «Сайты», и это не побочный эффект, а условие: сайтом
управляет docker-стек из этого репозитория, а не панель.

Итоговая схема:

```
браузер ──https──▶ Caddy (80/443, сертификат Let's Encrypt)
                     └──▶ web (Next.js, :8090)
                            └──▶ api (NestJS, :8091) ──▶ db (Postgres)
```

Наружу открыт только Caddy. `web` слушает `127.0.0.1:8090` (снаружи не
виден), `api` и `db` портов на хосте не занимают вовсе.

Почему всё идёт через Next, а не «сайт на web, API на api.домен»: браузер и
backend обязаны быть на одном origin. Кука сессии (`refresh_token`,
HttpOnly) ставится backend'ом, а проверяет её `frontend/src/proxy.ts` — гейт
защищённых страниц. На разных доменах эта кука до Next-сервера не доедет, и
проверять там будет нечего.

---

## 1. DNS в Vercel

В панели Vercel: **Domains → ваш домен → DNS Records** (не «Add to Project»).

| Type | Name | Value          | TTL |
|------|------|----------------|-----|
| A    | `@`  | IP вашего VPS  | 60  |
| A    | `www`| IP вашего VPS  | 60  |

Важное:

- **Не подключайте домен к проекту Vercel.** «Connect to Project» заставит
  Vercel отдавать по этому домену свой деплой, и трафик на VPS не пойдёт.
  Vercel здесь нужен только как DNS-хостинг.
- Домен должен использовать **nameservers Vercel** (`ns1.vercel-dns.com`,
  `ns2.vercel-dns.com`). Если домен куплен в Vercel — так уже есть; если
  зарегистрирован у другого регистратора — NS меняются у регистратора,
  и на распространение уходит до нескольких часов.
- Vercel DNS трафик не проксирует (это не Cloudflare), поэтому HTTPS
  терминируется на вашем VPS и сертификат выпускается там же.

Проверка (с любой машины, после распространения):

```bash
dig +short example.com          # должен вернуть IP вашего VPS
```

Пока `dig` возвращает не тот IP, шаг 4 делать бессмысленно: Let's Encrypt
проверяет владение доменом обращением на 80-й порт по этому же адресу.

## 2. Порты 80 и 443 на VPS

```bash
ss -ltnp | grep -E ':(80|443)\s'
```

- **Пусто** → вариант A (ниже), Caddy забирает порты себе. Это основной путь.
- **Занято nginx/apache панели** → либо освободить порты (панель тогда
  перестанет обслуживать свои сайты — так можно, только если их нет), либо
  вариант B: оставить порты панельному nginx и добавить ему конфиг руками,
  `deploy/nginx-virex.conf.example`. Домен на вкладке «Сайты» всё равно не
  появится — конфиг лежит в `/etc/nginx/conf.d/`, панель про него не знает.
  Обратная сторона варианта B: при обновлении панели свой конфиг стоит
  перепроверять (`nginx -t`).

Firewall: снаружи нужны только 22, 80 и 443. Порт 8090 публикуется на
loopback и в firewall не нуждается; 5432 наружу не публикуется вообще.

## 3. Конфиг сервера

```bash
cd /path/to/virex-trade
git pull
cp .env.prod.example .env.prod
chmod 600 .env.prod
```

Заполнить `.env.prod`. Секреты генерируются на сервере:

```bash
openssl rand -hex 24   # POSTGRES_PASSWORD
openssl rand -hex 32   # JWT_ACCESS_SECRET
openssl rand -hex 32   # CREDENTIALS_ENCRYPTION_KEY
```

`CREDENTIALS_ENCRYPTION_KEY` — мастер-ключ шифрования биржевых API-ключей
пользователей. Его потеря или замена означает, что все подключения к биржам
придётся заводить заново: строки в базе останутся, расшифровать их будет
нечем. Копию ключа держите там же, где остальные пароли от сервера.

## 4. Запуск

Вариант A (свой HTTPS через Caddy):

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml --profile edge up -d --build
```

Вариант B (HTTPS на nginx хоста):

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
sudo cp deploy/nginx-virex.conf.example /etc/nginx/conf.d/virex.conf
sudo sed -i 's/example\.com/ВАШ.ДОМЕН/g' /etc/nginx/conf.d/virex.conf
sudo certbot --nginx -d ВАШ.ДОМЕН -d www.ВАШ.ДОМЕН
sudo nginx -t && sudo systemctl reload nginx
```

Первая сборка занимает несколько минут (два multi-stage образа).

Проверка:

```bash
curl -I https://ВАШ.ДОМЕН                       # 200
docker compose -f docker-compose.prod.yml logs -f api   # старт NestJS без ошибок
```

Признак, что что-то не так с HTTPS: страница входа открывается, логин
проходит, но при переходе на `/overview` кидает обратно на `/login`. Значит,
кука сессии не сохранилась — она ставится с `secure`, и по http её браузер
выбрасывает. Лечится не приложением, а тем, чтобы сайт открывался по https
(в варианте B — заголовком `X-Forwarded-Proto`, он есть в примере конфига).

## 5. Обновление кода

```bash
git pull
docker compose --env-file .env.prod -f docker-compose.prod.yml --profile edge up -d --build
```

Схема БД синхронизируется на старте `api` (`prisma db push`). Миграций в
проекте нет; если очередное изменение схемы требует удаления колонки с
данными, `db push` откажется — это намеренно, `api` не поднимется, и данные
останутся целы. Разбираться с такой схемой нужно руками, а не флагом
`--accept-data-loss`.

## 6. Данные

Прод-стек живёт под именем проекта `virex-prod`, локальный — под именем
папки. Тома у них разные: **данные из dev-стека сами не переедут.** Если на
этом же сервере уже крутился `docker-compose.yml` и в нём есть нужная база:

```bash
# выгрузить из старого стека
docker compose -f docker-compose.yml exec -T db pg_dump -U virex virex > dump.sql
# залить в новый (api уже создал схему)
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T db \
  psql -U virex -d virex < dump.sql
```

Регулярный бэкап — той же командой `pg_dump` по cron. Дампы содержат хеши
паролей и зашифрованные ключи бирж: хранить рядом с `.env.prod` нельзя, иначе
украденный архив расшифровывается сам собой.

## 7. Что осталось известным ограничением

- **Лимит попыток входа считается по IP, а видит один IP.** `/auth/login` и
  `/auth/register` ограничены 10 попытками в минуту на адрес
  (`auth.controller.ts`), но до backend'а все запросы доходят от Next-сервера,
  а не от браузера. То есть лимит фактически общий на всех пользователей.
  На нынешнем размере аудитории это не мешает, но при росте лечится передачей
  реального адреса (`X-Forwarded-For`) и `trust proxy` в Nest.
- **Раздел «Боты» в прод-стек не входит** — его нет в `main`.
