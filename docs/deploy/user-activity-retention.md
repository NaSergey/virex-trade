# Срок хранения `user_activity_minutes` / `user_section_days` и выкладка T18

Контекст: `docs/superpowers/specs/2026-09-16-backend-optimization.md`, находка A8;
бриф — `.superpowers/sdd/2026-09-16-backend-optimization/task-18-brief.md`.

## Срок хранения

**180 дней.** Строки старше сметает `UsageCleanupService`
(`backend/src/admin/usage/usage-cleanup.service.ts`), только в роли `worker`
(и дефолтной `all`), раз в сутки. Константа — `ACTIVITY_RETENTION_DAYS` в
`backend/src/admin/usage/visits.ts`.

Откуда число:
- покрывает демо-аккаунт (`backend/src/scripts/seed-demo.ts` раскладывает
  историю на полгода) — иначе отчёт админки на демо-данных не совпадал бы до
  и после T18;
- совпадает по порядку величины с максимумом окна ретеншена
  (`RetentionQueryDto.weeks`, максимум 26 недель ≈ 182 дня) — отчёт удержания
  не должен упираться в стёртые строки раньше, чем в собственный лимит;
- достаточно, чтобы ответить на вопрос «пользуются сервисом или нет» без
  годовой истории поминутных засечек, которая и была самой быстрорастущей
  таблицей продукта (находка A8: 27–165 ГБ/год без срока жизни).

`countReturningUsers` и `queryActiveWeeks` (`backend/src/admin/usage/usage-queries.ts`)
сами подрезают нижнюю границу этим же порогом — не потому что отчёту нужно
именно 180 дней, а потому что за пределами окна строк для чтения и так уже
нет: сканировать то, чего сметатель не оставит, незачем.

## Первичный ключ: составной вместо суррогатного `id`

`UserActivityMinute` и `UserSectionDay` больше не имеют колонки `id`.
Первичный ключ — `@@id([userId, minute])` и `@@id([userId, day, section])`
соответственно, тот же приём и то же обоснование, что уже в схеме у
`PriceCandle`. Строка адресуется естественным ключом, к суррогатному `id`
никто не обращался.

## Выкладка на прод требует ручного шага

В проекте нет миграций — схема синхронизируется `prisma db push`, и на
проде эта команда идёт **неинтерактивно** при старте контейнера `api`
(`docker-compose.prod.yml`, `command`) **без** `--accept-data-loss`. Смена
первичного ключа на таблице с данными — операция с потерей данных, и без
этого флага `db push` откажется её выполнять, а `api` не поднимется вовсе
(упадёт в рестарт-луп).

Владелец решение принял: данные в этих двух таблицах аналитические, не
торговые и не восстанавливаемые из внешнего источника — разовая потеря
приемлема. Флаг `--accept-data-loss` в `docker-compose.prod.yml` **не
добавляется** постоянно (это ослабило бы защиту от случайной потери данных
для всех будущих схем) — вместо этого таблицы дропаются один раз вручную
перед выкладкой этой ветки, ровно по прецеденту миграции `price_candles`
(`docs/superpowers/plans/2026-09-10-btc-candles-storage.md`, шаг 5): после
`DROP TABLE` дропать уже нечего, и `db push` создаёт таблицы заново без
вопроса о потере данных.

**Перед выкладкой этой ветки на прод, один раз:**

```
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T db \
  psql -U virex -d virex -c \
  "DROP TABLE IF EXISTS user_activity_minutes, user_section_days;"
```

Дальше обычный деплой: `git push` на прод-remote выкладывает код, но
контейнеры сам не перезапускает — пересборка и рестарт `api`/`worker`
делаются вручную (`docker compose ... up -d --build`). После рестарта `api`
поднимется, `db push` создаст обе таблицы уже с составным ключом, история
активности начнётся с чистого листа.

**Локально** — тот же порядок, если в локальной БД уже есть строки в этих
таблицах и `docker compose up` откажется стартовать `api` с вопросом про
`--accept-data-loss`:

```
docker compose exec -T db psql -U virex -d virex -c \
  "DROP TABLE IF EXISTS user_activity_minutes, user_section_days;"
```

После этого `npx prisma db push` (или обычный старт контейнера) проходит
чисто.
