# Entry/exit quality

## Проблема

Разбор конкурентов ([[virex_competitor_landscape]]) показал: у Edgewonk есть отдельная
метрика качества входа и выхода — «насколько близко к оптимальной цене» — как самостоятельный
вопрос, отдельный от того, вышла ли сделка в плюс. У Virex такой метрики нет вовсе, хотя
сырьё для неё уже есть: `rangePos()` в
[trade-context.service.ts:149-161](../../../backend/src/trades/trade-context.service.ts)
считает «где цена встала в диапазоне последних N свечей», просто применяется только к
входу и только к свечам ДО него.

Обсуждение в чате закрыло главный вопрос: считать не относительно произвольного окна
истории до входа (как `rangePos`), а **относительно самой сделки** — от входа до выхода.
Это отвечает на «мог ли я войти/выйти лучше», а не на «продал на силе или слабости
относительно недавнего».

## Решение

### Формула — направленное переиспользование `rangePos`

Окно — экстремумы свечей **между входом и выходом** сделки (не до входа, как у
`rangePos`):

```
windowLow  = min(low)  по свечам [entryMs, closedAt]
windowHigh = max(high) по тем же свечам
pos(price) = (price − windowLow) / (windowHigh − windowLow) × 100
```

Направление решает, что считать качеством:

- **Лонг:** `entryQuality = 100 − pos(entryPrice)` (вход ближе к низу — лучше),
  `exitQuality = pos(exitPrice)` (выход ближе к верху — лучше).
- **Шорт:** зеркально — `entryQuality = pos(entryPrice)`, `exitQuality = 100 − pos(exitPrice)`.

В отличие от `rangePos`, которая намеренно НЕ клампится (пробой диапазона — сигнал), здесь
результат **клампится в [0, 100]**: окно определено самой сделкой, и цена входа/выхода
физически не может лежать вне свечи, в которую сама попала — выход за границы означал бы
только числовую погрешность, а не находку.

### Гранулярность окна — по длительности сделки

Один и тот же скальп на 5 минут и свинг на две недели нельзя мерить одной свечой — на
дневках скальп внутри одной свечи, на минутках свинг — это 4000 точек без всякого смысла.

| Держал | Свечи | Источник |
|---|---|---|
| < 4ч | 5м | Новый фетч, батчится по символу (не по сделке) |
| 4ч – 3д | 15м | Отдельный фетч, тот же принцип |
| 3д – 30д | 1ч | Отдельный фетч |
| ≥ 30д | 4ч | Отдельный фетч |

Первая версия этой спеки предполагала переиспользовать уже идущие ради `rangePos` запросы
свечей (m15/h1/h4), раздвинув их верхнюю границу до выхода сделки — это дешевле по числу
запросов к Bybit, но означает трогать fetch-диапазоны `computeSymbol()`, от которых уже
зависит работающий `rangePos`/`IndicatorsService.computeSnapshot`. Решено **не рисковать
работающим кодом ради экономии part API-вызовов** — новая метрика получает полностью
независимый, свой набор запросов свечей. Общий с существующим кодом — только сам паттерн
батчинга («один фетч на символ за тик, не на сделку»), не данные.

### Где считается

Новый приватный шаг в `TradeContextService`, вызываемый в конце уже существующего
`computeMissing()` ([trade-context.service.ts:181-216](../../../backend/src/trades/trade-context.service.ts)) —
после того, как обычный контекст (`rangePos`/индикаторы) досчитан. `TradeSyncService` его уже
вызывает раз за тик ([trade-sync.service.ts:176](../../../backend/src/trades/trade-sync.service.ts)) —
менять вызывающий код не нужно.

Не может жить в `buildSnapshot()` — эта функция общая с `snapshotNow()` для ещё открытых
позиций, а `closedAt`/`avgExitPrice` у открытой позиции просто не существует.

```ts
// Границы длительности сделки для выбора ТФ окна качества.
const QUALITY_SCALP_MS = 4 * H1_MS;      // < 4ч — 5-минутки
const QUALITY_INTRADAY_MS = 3 * D1_MS;   // 4ч–3д — 15м
const QUALITY_SWING_MS = 30 * D1_MS;     // 3д–30д — 1ч
                                          // ≥30д — 4ч
const QUALITY_INTERVALS = [
  { maxMs: QUALITY_SCALP_MS, interval: '5', tfMs: 5 * 60_000 },
  { maxMs: QUALITY_INTRADAY_MS, interval: '15', tfMs: M15_MS },
  { maxMs: QUALITY_SWING_MS, interval: '60', tfMs: H1_MS },
  { maxMs: Infinity, interval: '240', tfMs: H4_MS },
];
const QUALITY_MIN_CANDLES = 3; // меньше — окно из 1-2 свечей, не диапазон

function qualityIntervalFor(holdMs: number) {
  return QUALITY_INTERVALS.find((b) => holdMs < b.maxMs)!;
}

/** Направленное pos(): 100 − сырое значение для входа-лонга и выхода-шорта. */
function directedPos(raw: number, invert: boolean): number {
  const v = invert ? 100 - raw : raw;
  return Math.max(0, Math.min(100, v));
}
```

Группировка — по паре (symbol, interval), не по символу: сделки одного символа с разной
длительностью полностью выпадают в разные корзины ТФ и в разные запросы свечей. Внутри
группы фетч один — `getKlinesRange(symbol, interval, min(entryMs), max(closedAt))` —
[bybit-market.service.ts:151](../../../backend/src/bybit/services/bybit-market.service.ts)
уже поддерживает произвольный интервал и пагинацию, новой инфраструктуры не требует.

### Отметка «посчитано», не просто «есть значение»

`entryQuality`/`exitQuality` могут законно оказаться `null` (меньше `QUALITY_MIN_CANDLES`
свечей в окне) — этот `null` нельзя отличить от «ещё не пытались посчитать» без отдельного
флага, иначе такая сделка будет пересчитываться (и дёргать API) на каждом тике вечно. Новое
поле `TradeContext.qualityComputed: Boolean @default(false)` — тот же приём, что уже решает
эту проблему для всего снимка через `ok`/`ctxVersion`.

### Модель — расширение `TradeContext`, не новая таблица

`TradeContext` уже 1:1 с `Trade`
([schema.prisma:238-269](../../../backend/prisma/schema.prisma)) и уже хранит `rangePos*` —
концептуальный сосед. Три новых поля:

```prisma
model TradeContext {
  // ...существующие поля без изменений...

  /// Качество входа/выхода относительно диапазона самой сделки (вход→выход),
  /// не относительно истории до входа, как rangePos. 0..100, клампится (не как
  /// rangePos — здесь выход за границы означал бы только погрешность).
  /// null — meньше QUALITY_MIN_CANDLES свечей в окне сделки.
  entryQuality Float?
  exitQuality  Float?
  /// true — попытка расчёта уже была (успешная или нет). Отличает «посчитан
  /// null, потому что данных мало» от «ещё не пытались» — без этого пустые
  /// пересчитывались бы на каждом тике синка.
  qualityComputed Boolean @default(false)
}
```

### Наружу — API и Обзор

- `TradesService.list()` — добавить `entryQuality`/`exitQuality` в allowlist контекста
  ([trades.service.ts:151-163](../../../backend/src/trades/trades.service.ts)), тем же
  способом, что и `rangePos1h` там же — раскрытая строка журнала получает два новых числа
  рядом с уже показанным диапазоном входа.
- `TradesService.stats()` — сейчас **не запрашивает контекст вообще** (`prisma.trade.findMany`
  без `include: { context: true }`,
  [trades.service.ts:746-751](../../../backend/src/trades/trades.service.ts)) — добавить
  `include`, посчитать `avgEntryQuality`/`avgExitQuality` как среднее по сделкам периода,
  где значение не `null` (отдельный счётчик знаменателя, не `totalTrades` — не у каждой
  сделки есть контекст). Два новых поля `TradeStats`, две новые ячейки `SummaryStrip` —
  **раздельно**, не одним числом: продукт целиком построен на разделении «на чём ошибся» и
  «что получилось», сливать в одну цифру значило бы спрятать, какая именно половина хромает.
  Ячейки — сразу после Edge Score (третьей и четвёртой): это тоже число про качество
  исполнения, им место рядом, а не в хвосте рядом с Fees/Best/Worst.
- Оба фронтовых типа-копии — `frontend/src/entities/trade/api/types.ts` (`TradeContext` —
  `entryQuality`/`exitQuality`; `TradeStats` — `avgEntryQuality`/`avgExitQuality`) — тем же
  принципом копирования без общего пакета типов, что и везде в проекте.

## Что не меняется

- `rangePos*`, `IndicatorsService.computeSnapshot`, fetch-диапазоны `computeSymbol()` — не
  трогаются вообще. Новая метрика физически не пересекается с их кодом, только с тем же
  файлом и той же Prisma-моделью.
- `snapshotNow()` (контекст открытой позиции) — без изменений: качество входа/выхода
  принципиально недоступно, пока сделка не закрыта.
- `LabService`/Аналитика — контекст туда не добавляется в этой задаче: спека и обсуждение
  ограничили вывод раскрытой строкой журнала и агрегатом на Обзоре.

## Риски / на что смотреть при реализации

- **Составная позиция (несколько частичных закрытий) — `exitQuality` берётся с первой
  части.** `collapseToPositions`
  ([positions.ts:160-174](../../../backend/src/trades/positions.ts)) строит результат через
  `{...first, ...}` и не переопределяет `context` — при нескольких частях у позиции
  `avgExitPrice`/`closedAt` результата блендированные, а `context.exitQuality` — от первого
  частичного выхода, не пересчитанное под блендированную цену. `entryQuality` эту проблему
  не имеет (вход обычно один момент на все части). Обычная сделка (`parts: 1`) — большинство
  — корректна; составные — известное, принятое огрубление, не считается отдельно.
- **Дополнительные API-вызовы.** Каждый батч-тик — до 4 новых запросов свечей на символ
  (по одному на реально встретившуюся корзину длительности), сверх уже идущих пяти
  (m15/m30/h1/h4/d1). Осознанный выбор в пользу изоляции от рабочего кода, не оптимизация.
- **Гейт `QUALITY_MIN_CANDLES = 3`** — подобран, не выведен: меньше — окно из 1-2 свечей
  технически «диапазон», но бессмысленный. Тест обязан проверить именно границу (2 свечи →
  `null`, 3 → считается).
