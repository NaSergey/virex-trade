# История баланса и декларации числовых правил

Дата: 2026-08-27

## Контекст

CLAUDE.md разделяет продукт по типу правила: качественное («почему вошёл») — теги, числовое и
проверяемое («сколько рисковал») — декларация плюс автопроверка. Реализована сегодня только
первая половина. Второй нет ни в каком виде: в `schema.prisma` пятнадцать моделей, и ни одной
под правило или под баланс.

Разбор рынка на 2026-08-27 показал, что это единственное незанятое отличие продукта.
Автоимпорт по read-only ключам, мультибиржевость и точный учёт фандинга — базовая функция у
tradesviz.com, tradersync.com, plancana.com, tradetrack.space и других. Декларации с
автопроверкой нет ни у кого из найденных.

Что уже есть в коде и на что опирается дизайн:

- `getBalance` в интерфейсе адаптера (`exchange.types.ts`), реализован всеми семью адаптерами.
  Сейчас его дёргает только контроллер, показывая текущий баланс. Не хватает не чтения, а
  хранения во времени.
- `TradeSyncService` обходит всех подключённых пользователей раз в 60 секунд — готовый цикл,
  куда вешается снятие снимков.
- `TradeContext` — образец таблицы 1:1 к `Trade` с версией набора полей и правилом «считаем
  только тем, у кого ещё нет».
- `OpenPositionSeen` снимает состояние позиции на первом тике её жизни. Туда же ляжет стоп.
- `loadRows(tzOffsetMin)` в `trade-rows.ts` — конвенция границы суток: сутки и день недели в
  локальной зоне пользователя, торговые сессии в UTC.
- `HabitsService` уже отвечает на вопрос «сколько это стоило» контрфактуалом с перестановочным
  тестом и поправкой Бенджамини–Хохберга.

Чего нет и что определило дизайн: **стоп-лосс нигде не сохраняется**. `OpenPosition.stopLoss`
существует в живой форме адаптера, но ни `OpenPositionSeen`, ни `Trade` его не пишут. Поэтому
«риск в % от депозита» в каноническом смысле — «если сработает стоп, потеряю столько» — на
сегодняшних данных не вычислим.

## Решения

Все приняты в обсуждении с пользователем 2026-08-27.

- **Форма правила:** метрика + оператор + порог. Одна таблица `Rule`, каталог метрик — константа
  в коде. Не фиксированный набор колонок (каждое новое правило = миграция) и не движок выражений
  (парсер, песочница, объяснение нарушений).
- **Источник баланса:** снимки вперёд плюс реконструкция назад по цепочке PnL. Каждая точка
  помечена источником, расчётные подписаны в интерфейсе как оценка.
- **Реакция на нарушение:** только ретроспектива — экран соблюдения и отметка в журнале.
  Telegram-предупреждение в момент нарушения обсуждалось и в объём v1 не входит; дизайн
  оставляет для него шов.
- **Смысл риска:** две метрики в каталоге. `exposure_pct` считается на всей истории уже сегодня,
  `planned_risk_pct` появляется у сделок со стопом после релиза.
- **Где считать:** материализуются метрики, не нарушения. Дорогая и стабильная часть (найти
  баланс на момент входа) считается один раз, дешёвая и волатильная (сравнить с порогом) — на
  чтение.
- **Цены нарушений в долларах в v1 нет.** Обоснование — в разделе «Границы».

## Архитектура

### Модель данных

```prisma
model BalanceSnapshot {
  id       String   @id @default(uuid())
  userId   String
  user     User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  exchange String
  at       DateTime
  balance  Float
  // 'snapshot' — спросили биржу, 'derived' — вывели из цепочки PnL
  source   String
  // Неторговое изменение баланса: ввод или вывод средств. Null, пока разрыва нет.
  gap      Float?
  @@unique([userId, exchange, at])
  @@index([userId, exchange, at])
  @@map("balance_snapshots")
}

model TradeRisk {
  id             String   @id @default(uuid())
  tradeId        String   @unique
  trade          Trade    @relation(fields: [tradeId], references: [id], onDelete: Cascade)
  balanceAtEntry Float?
  balanceSource  String   // 'snapshot' | 'derived'
  exposurePct    Float?
  plannedRiskPct Float?   // null у сделки без стопа
  ok             Boolean  @default(true)  // false — баланс на тот момент неизвестен
  riskVersion    Int      @default(1)
  computedAt     DateTime @default(now())
  @@map("trade_risks")
}

model Rule {
  id        String   @id @default(uuid())
  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  metric    String   // ключ из каталога метрик в коде
  operator  String   // 'lte' | 'gte'
  threshold Float
  active    Boolean  @default(true)
  createdAt DateTime @default(now())
  @@unique([userId, metric])
  @@index([userId, active])
  @@map("rules")
}
```

Дополнения к существующим моделям:

- `OpenPositionSeen.stopLoss Float?` — снимается там же, где сейчас снимается `entryPrice`.
- `Trade.stopLoss Float?` — переносится из `OpenPositionSeen` при закрытии, ровно как `openedAt`.

`Rule` не хранит окно. Окно — свойство метрики, а не правила: `exposure_pct` бывает только на
сделку, `trades_per_day` только на день. Отдельное поле разрешило бы в базе комбинации вроде
«экспозиция за неделю», которые ничего не значат и отсеивались бы валидацией.

`@@unique([userId, metric])` — одно правило на метрику. «Риск ≤ 2%» и «риск ≤ 5%» одновременно
не декларация, а её отсутствие.

### Баланс: якоря и вывод

Снимки — не сам ряд, а якоря. Раз баланс в любой момент выводится из цепочки сделок, частота
опроса не определяет точность. Якоря нужны, чтобы ловить снос и обнаруживать ввод и вывод
средств.

Частота — **раз в час**, отдельным таймером рядом с `TradeSyncService`. Не 60 секунд: 1440
строк в сутки на пользователя не дают ничего сверх вывода по PnL. Не раз в сутки: якорь должен
быть достаточно частым, чтобы разрыв от пополнения локализовался в узкое окно.

Для каждого нового якоря считается ожидание:

```
ожидание = предыдущий якорь + Σ(closedPnl, комиссии, фандинг между ними)
```

Расхождение сверх допуска — деньги, которые не приторговали. Оно пишется в `gap`, и **цепочка
вывода через разрыв не продолжается**: каждый разрыв начинает новый отрезок, поэтому одно
пополнение не искажает весь ряд назад.

Допуск — константа, и подбирается он не под округление, а под нереализованный PnL: если
`getBalance` возвращает баланс кошелька вместе с плавающей прибылью открытых позиций, якорь
будет дышать вместе с рынком, и каждый вдох код прочитает как пополнение. Что именно возвращают
адаптеры — `balance` или `availableToWithdraw`, с нереализованным или без, — проверяется до
реализации (см. «Тестирование»). Если стабильного поля нет ни у одной биржи, якорь снимается
только когда открытых позиций нет, а часовой таймер пропускает тик.

Реконструкция назад — тот же механизм от самого раннего якоря в прошлое. Ввод и вывод до
первого якоря невидимы и сдвигают весь ранний отрезок целиком; поэтому `source` доезжает до
интерфейса и расчётные числа подписаны как оценка.

### Каталог метрик v1

Константа в коде. Каждая запись объявляет ключ, окно, единицу, подпись и функцию вычисления.

| ключ | окно | формула | доступность |
|---|---|---|---|
| `exposure_pct` | сделка | `qty × avgEntryPrice / balanceAtEntry` | вся история |
| `planned_risk_pct` | сделка | `qty × abs(avgEntryPrice − stopLoss) / balanceAtEntry` | сделки со стопом после релиза |
| `leverage` | сделка | `Trade.leverage` | вся история, где биржа его отдала |
| `trades_per_day` | день | число закрытий за сутки | вся история |
| `daily_loss_pct` | день | `Σ PnL за сутки / баланс на начало суток` | вся история |

Дневные метрики считаются по локальной зоне пользователя через `tzOffsetMin`, как это уже
делает `loadRows`.

### Семантика проверки

Сделка, у которой метрика `null` — нет стопа, неизвестен баланс на входе, биржа не отдала
плечо, — **не считается ни нарушением, ни соблюдением**. Она выпадает и из числителя, и из
знаменателя, а её количество показывается рядом с долей: «соблюдено в 39 из 50; ещё 12 сделок
не проверялись — нет стопа».

Молча засчитывать непроверенное как соблюдение недопустимо: это ровно тот случай, когда
продукт врёт в приятную сторону, а доверие к декларации — единственное, ради чего она нужна.

### Поток данных

1. Часовой таймер снимает `getBalance` у активной биржи каждого подключённого пользователя,
   пишет `BalanceSnapshot(source: 'snapshot')`, сверяет с ожиданием, при расхождении ставит `gap`.
2. `TradeSyncService` при вставке новой закрытой сделки переносит `stopLoss` из
   `OpenPositionSeen`, как переносит `openedAt`.
3. Сервис расчёта риска добирает сделки без `TradeRisk` (или с устаревшим `riskVersion`),
   находит баланс на момент входа — якорь либо вывод, — считает `exposurePct` и
   `plannedRiskPct`, пишет `TradeRisk`.
4. Экран соблюдения и журнал читают `Rule` и сравнивают с готовыми числами из `TradeRisk`.
   Правило можно править и выключать без пересчёта истории.

Материализуются только метрики уровня сделки. Дневные (`trades_per_day`, `daily_loss_pct`)
считаются на чтение группировкой по суткам: они зависят от `tzOffsetMin`, который приходит с
запросом, и хранить их значило бы хранить одно и то же число в стольких копиях, сколько
часовых поясов у пользователя за жизнь.

### Интерфейс

- **Настройки** — новая секция под биржами: список деклараций и форма добавления (метрика из
  списка, оператор, порог). Декларация это настроечный акт, делается один раз.
- **Обзор** — блок «Соблюдение правил» за уже выбранный на странице период: по каждому активному
  правилу доля соблюдения, число непроверенных, порог. Обзор, а не отдельная страница, потому
  что это стартовый экран, и «система учит» работает, только если человек видит это, никуда не
  переходя.
- **Журнал сделок** — в раскрытой строке отметка, какие правила нарушила эта сделка и с каким
  значением: «экспозиция 14.2% при вашем пороге 5%».

Вся разметка — через `shared/ui` (`Field`, `Select`, `Input`, `Button`, `SectionHead`,
`KeyValue`, `EmptyState`), цвета классами из `globals.css`. Блок соблюдения живёт в
`views/overview/components/`, а не в `widgets/`: он используется на одной странице.

## Обработка ошибок

- **Биржа не ответила на `getBalance`.** Якорь за этот час не пишется. Пропуск не ошибка: вывод
  по цепочке PnL закрывает дыру, а следующий успешный якорь заодно проверит отрезок.
- **Баланс на момент входа неизвестен** (сделка раньше первого якоря и цепочка оборвана
  разрывом). `TradeRisk.ok = false`, метрики `null`, сделка выпадает из проверки и попадает в
  счётчик непроверенных.
- **Стопа нет** — `plannedRiskPct = null`. Отдельно от `ok = false`: баланс известен,
  `exposurePct` посчитан, не хватает только стопа.
- **Позиция открылась при лежащем сервере** — нет `OpenPositionSeen`, значит нет ни `openedAt`,
  ни `stopLoss`. Тот же прецедент, что и сегодня с `openedAt`.
- **Баланс на начало суток неизвестен** — `daily_loss_pct` за эти сутки не считается, день
  выпадает из проверки и попадает в счётчик непроверенных, как и сделка без баланса. Правило
  «дневной убыток ≤ 5%» на дне без баланса не нарушено и не соблюдено.
- **Правило ссылается на метрику, которой нет в каталоге** (откат версии кода) — правило
  показывается выключенным с пояснением, а не роняет экран.

## Тестирование

Первым пишется тест на **двойной учёт комиссий**. Нужно проверить по каждому адаптеру, входят
ли комиссии в `closedPnl`; у Bybit — входят. Если вычесть их вторым разом, цепочка вывода
поедет, а поехавшую цепочку код прочитает как ввод средств. Ошибка здесь не «немного неточно»,
а «выдуманные пополнения в истории пользователя».

Вторым — тест на **нереализованный PnL в балансе**. По каждому адаптеру выясняется, что именно
возвращает `getBalance`: баланс кошелька с плавающей прибылью открытых позиций или без неё.
Если с ней, якорь дышит вместе с рынком, и каждое движение цены код прочитает как ввод или
вывод средств. Симптом тот же, что у двойного учёта комиссий, поэтому оба проверяются до того,
как будет написана логика разрывов.

Дальше:

- Вывод баланса назад по известной цепочке сделок даёт ожидаемый ряд.
- Пополнение между якорями распознаётся как `gap`, и отрезок до него не сдвигается.
- Сделка без стопа: `exposurePct` посчитан, `plannedRiskPct` — `null`, `ok = true`.
- Сделка вне зоны известного баланса: `ok = false`, обе метрики `null`.
- Доля соблюдения не считает непроверенные сделки ни в числителе, ни в знаменателе.
- Дневные метрики режут сутки по `tzOffsetMin`, а не по UTC.
- Смена порога правила меняет долю соблюдения без пересчёта `TradeRisk`.

## Границы

**Цены нарушений в долларах в v1 нет.** Соблазн показать «нарушения стоили вам $412» — это
сумма PnL нарушивших сделок, а `HabitsService` в этом же коде прямо объясняет, почему так
делать нельзя: у убыточного счёта убыточен любой срез, и число получится убедительным и
бессмысленным. Правильный ответ на вопрос «сколько это стоило» уже написан — контрфактуал с
перестановочным тестом в «Цене привычек». Дублировать его слабой версией хуже, чем не отвечать.

**Telegram-предупреждение в момент нарушения — не в v1.** Инфраструктура для него есть
(`TelegramService`, уведомления об открытии позиции, `OpenPositionSeen` как защита от повтора),
и дизайн оставляет шов: расчёт метрики на открытой позиции отличается от расчёта на закрытой
только источником `qty` и цены входа.

**Ввод и вывод средств не читаются с биржи.** Они выводятся из расхождения якоря с ожиданием.
Пополнение и вывод в один час на близкие суммы взаимно погасятся и останутся невидимыми.
Читать историю транзакций с биржи — отдельная работа, требующая нового метода в интерфейсе
адаптера и реализации во всех семи.

**Стоп «в голове» не виден.** Метрика `planned_risk_pct` работает только у тех, кто выставляет
стоп на бирже. Для остальных раздел покажет непроверенные сделки, а не ноль нарушений.
