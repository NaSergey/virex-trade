# Панель ордера бектеста: слайдеры риска/стопа/тейка и размер в монете

## Контекст и что не входит в этот проект

Запрос был «перенести панели торгового терминала (график и панель) из E:\git\traders,
со своим дизайном». По итогам обсуждения расклад такой:

- **График остаётся как есть.** `ReplayChart.tsx` — своё SVG (обязательное правило проекта:
  «графики — своё SVG», см. CLAUDE.md), уже умеет пан/зум/драг уровней. Терминал в traders
  использует `lightweight-charts` — на неё не переходим. Инструменты рисования (трендлиния,
  фибо, линейка) и контекстное меню по клику на график — тоже не переносятся: осознанно
  отложено, не требуется сейчас.
- **Грид/DCA-калькулятор не переносится.** У него в traders отдельный симуляционный движок
  (лесенка ордеров, усреднение, циклы) в `BacktestService` на бэкенде traders-api. Движок
  бектеста virex (`useReplay.ts`, `lib/fills.ts`) умеет ровно одну открытую позицию —
  вход/стоп/тейк, без концепции нескольких ордеров. Построить второй движок под грид/DCA —
  отдельный проект, будет рассмотрен отдельно (возможно, вместе с веткой `feat/dca-grid-bot`,
  если/когда боты дойдут до продукта).
- **Работа этого проекта — панель ордера `OrderPanel.tsx`.** Приблизить её к тому, как
  выглядит и считает `SimpleCalculator` в traders (слайдер риска, слайдеры для стопа/тейка,
  размер позиции в монете и в USDT сразу), но на своих компонентах (`shared/ui`, токены
  `globals.css`), без Tailwind-классов traders.

## Компонент `Slider` (новый, `frontend/src/shared/ui/Slider.tsx`)

Простой контролируемый range-инпут поверх нативного `<input type="range">` — без сторонней
библиотеки (в traders `Slider` тоже свой, но на Tailwind; здесь пишем заново на токенах
`globals.css`).

```ts
interface SliderProps {
  value: number;
  min: number;
  max: number;
  step?: number;
  onChange: (value: number) => void;
  className?: string;
  disabled?: boolean;
}
```

- Трек — `--color-line`, заполненная часть до значения — `--color-accent` (через
  `background: linear-gradient` с расчётным процентом, пересчитывается на каждый рендер —
  без стороннего состояния).
- Ползунок — квадратный (в системе `--radius-* : 0px` везде, круглый ползунок будет выбиваться
  из стиля), `--color-fg`, увеличивается на hover/focus для доступности клика.
- Высота трека и ползунка — фиксированные, компактные (под однострочный ряд рядом с полем
  ввода), никакой адаптации под мобильный `u = W / boxW` не нужно — это HTML-контрол, не SVG.
- Клавиатура работает из коробки (нативный range: стрелки меняют value на `step`).

Компонент ничего не знает про риск/стоп/тейк — чистый контрол значения в диапазоне, как
`Input`/`Select` в `Field.tsx`.

## Изменения `OrderPanel.tsx`

### Риск

Было: `Field label={t('risk')}` → голый `Input`.

Стало: та же `Field`, но рядом с подписью — `Slider` (0–10%, step 0.1), а под ним — `Input`
(текстовое поле остаётся, чтобы можно было ввести точное число, как сейчас). Слайдер и поле
синхронизированы через общий `draft.risk`: движение слайдера пишет туда же, что и ручной ввод.
Диапазон 0–10 фиксированный, не зависит от баланса — как в traders (`RiskSection`, `min={0}
max={10}`).

Рядом с процентом — сумма риска в USDT (`preview.riskUsdt`, уже считается): раньше блок
`preview` показывался только когда есть непустой стоп, теперь строку риска в USDT выводим
всегда, когда риск и цена известны, даже без стопа — чтобы слайдер сразу отзывался числом.

### Стоп и тейк

Оба поля получают такой же `Slider` рядом с подписью. Диапазон:

- **Стоп** — по правильную сторону от цены входа/текущей цены, ширина ±20% (шире, чем в
  traders, где ±10% — там инструмент для реальной торговли с более узкими стопами; в
  бектесте пользователь может осознанно тестировать более широкие стопы).
  - Long: `[price * 0.8, price)`
  - Short: `(price, price * 1.2]`
- **Тейк** — по своей стороне, тот же диапазон ±20%, без верхней логической границы (R:R
  не ограничен, но слайдер обязан иметь конечные min/max — берём тот же процент, что и у
  стопа, для симметрии виджета; кто хочет тейк дальше — впечатывает числом в поле, слайдер
  просто не дотянется до края).
  - Long: `(price, price * 1.2]`
  - Short: `[price * 0.8, price)`

`price` — экранная цена (`toScreen(replay.price, scale)`), она уже приходит в `OrderPanel`
как проп `price`. Если `price == null` (график ещё не готов) — слайдер получает `disabled`.

Драг уровня прямо на графике (`onDragLevel`) — как сейчас, работает независимо и пишет в тот
же `draft`, поэтому слайдер в панели просто отражает актуальное значение при следующем рендере
— двух источников правды не появляется.

### Размер позиции

Было: `notional`, `leverage`, `riskUsdt` (последнее становится общим для риск-секции, см.
выше — не дублируется).

Стало: карточка (`div` с классом вроде `.size-preview`, стили — бордер `--color-line`, фон
`--color-elevated`, паддинг `--s2`/`--s3`) с двумя строками:

- размер в монете: `preview.qty`, отформатировано так же, как остальные числовые значения
  продукта (без явного тикера — сессия ведётся в паре, у бектеста нет мультивалютности на
  экране);
- размер в USDT: `preview.notional` (как было).

Плечо (`preview.leverage`) остаётся отдельной строкой ниже карточки, как сейчас (справочное,
подпись не меняется).

## i18n

Один новый ключ в `frontend/src/shared/i18n/messages/{ru,en}.json`, неймспейс `backtest`:

- `sizeCoin` — подпись строки размера в монете в карточке предпросмотра.

Остальные подписи переиспользуются как есть: `riskAmountLabel` (уже существует, просто
начинает показываться раньше — не только при заполненном стопе), `notionalLabel`,
`leverageLabel`, `risk`, `stop`, `take`.

## Тестирование

Чистых функций с новой логикой не появляется — диапазоны стопа/тейка считаются инлайн в
компоненте по `price`/`direction`, `previewSize` в `lib/money.ts` не меняется (просто
достаём уже посчитанное поле `qty`, которое раньше не выводилось). Юнит-тестов не требуется;
проверка — вручную через дев-сервер (открыть активную сессию бектеста, подвигать слайдеры,
свериться со значениями полей и карточки).

Правка укладывается в «мелкое изменение» из глобальных правил (1–2 файла + новый компонент
без новых зависимостей) — полный `next build` не гоняем, ограничиваемся `tsc`/точечной
проверкой; если понадобится больше файлов или всплывёт что-то на конфиг — скажу отдельно.
