# Оптимизация бэкенда под 1000 онлайн

Дата: 2026-09-16
Ветка: `perf/backend-optimization`

## Что спрашивается

Выдержит ли бэкенд **1000 пользователей одновременно онлайн** (открытые вкладки с
поллингом) и произвольное число зарегистрированных аккаунтов с подключёнными биржами
(фоновый синк к «онлайн» не привязан). Инфраструктура — одна VPS,
`docker-compose.prod.yml`: `db` + `api` + `web` + `caddy` на одном хосте, Postgres без
реплик, Redis и очередей задач нет.

Ответ короткий: **сегодня не выдержит, и упирается не в железо**. Три из четырёх узких
мест — это работа, которая делается заново на каждый запрос при неизменившихся данных, и
последовательные циклы там, где ждут сеть. После их починки 1000 онлайн помещаются на
одном приличном VPS с запасом, и ни Redis, ни BullMQ, ни вторая машина для этого не
нужны.

## Целевая нагрузка, посчитанная, а не названная

Частоты поллинга взяты из фронта (`refetchInterval`), не из головы.

| Что | Откуда | Раз в минуту на вкладку |
|---|---|---|
| `/api/exchange/positions` | `entities/position/api/hooks.ts:23` — 30 с | 2 |
| `/api/trades` | `entities/trade/api/hooks.ts:31` — 60 с | 1 |
| `/api/trades/stats` | там же (`LIVE`) | 1 |
| `/api/trades/stats-by-time` | там же | 1 |
| `/api/trades/open-context` | `entities/position/api/hooks.ts:37` — 60 с | 0–2 |
| `/auth/refresh` | `JWT_ACCESS_TTL=15m` | 0.07 |

Вкладка «Обзора» — **≈6 запросов в минуту**. Тысяча онлайн → **6000 req/min ≈ 100 req/s**,
с переходами по разделам («Рынок», «Аналитика», «Теги») пики до 150 req/s.

Сто запросов в секунду — это немного. Один Node-процесс отдаёт такое, **если каждый
запрос стоит миллисекунды**. У нас три из шести запросов вкладки читают всю торговую
историю пользователя целиком.

### Объём данных при 1000 подключённых аккаунтов

Умеренно активный трейдер за полгода: ~550 позиций, ~900 строк `trades`, ~2000 строк
`executions`. Тогда:

- `trades` ≈ 0.9 млн строк, `executions` ≈ 2 млн, `trade_contexts` ≈ 0.9 млн — для
  Postgres это мелочь;
- `price_candles` — уже ~5.9 млн строк (см. комментарий в схеме), растёт на ~0.5 млн в
  год, тоже мелочь;
- `user_activity_minutes` — **единственная таблица, которая при 1000 онлайн растёт
  опасно**: строка на пользователя на минуту. Считаем ниже (находка A8).

### Где ломается сегодня

**HTTP.** Три «живых» агрегата «Обзора» (`stats`, `stats-by-time`, `trades`) делают
`findMany` по всей истории **без `select`**, то есть вместе со столбцом `Trade.raw` —
сырой записью биржи (~450 байт JSON на строку, которую никто не читает). 900 строк ×
450 B = **405 КБ мусора на запрос**. Три запроса в минуту на тысячу пользователей — это
50 req/s × 900 строк = **45 000 строк/с** из `trades` и ~20 МБ/с сырого JSON, который
Prisma разбирает и выбрасывает. По CPU это 25–60 мс на запрос → **2–3 секунды работы на
каждую секунду времени** на единственном потоке. Процесс перегружен втрое ещё до того,
как запустились фоновые циклы.

**Синк.** `TradeSyncService.syncAll` (`trade-sync.service.ts:79`) идёт последовательным
`for` по всем подключённым пользователям. На пользователя приходится **минимум четыре
HTTPS-запроса к бирже** (закрытые сделки, филлы, открытые позиции — и позиции
запрашиваются **дважды**, см. A3) и **около двадцати запросов в БД**, два из которых
читают всю историю исполнений и все сделки пользователя. При 250 мс на сетевой вызов
один пользователь занимает ~1 с. Значит, **цикл перестаёт помещаться в свои 60 секунд
примерно на 60 подключённых аккаунтах**, а не на тысяче. Дальше `sweeping` глотает тики,
и синк тихо разъезжается с обещанной минутой.

**База.** Суммарно в установившемся режиме при 1000 онлайн / 1000 подключённых:
~100 q/s (HTTP) + ~333 q/s (синк) + ~93 q/s (рыночные сигналы) + ~83 q/s (трекер
активности) + ~66 q/s (чтение кредов) ≈ **680 запросов в секунду** на пуле, размер
которого нигде не задан: `connection_limit` отсутствует в `DATABASE_URL`, то есть
Prisma берёт дефолт `num_cpus * 2 + 1` — **девять соединений** на 4-vCPU машине. Часть
этих запросов держит соединение десятки миллисекунд (те самые чтения всей истории), и
пул выедается до `P2024 Timed out fetching a new connection` задолго до тысячи.

**Лишний сетевой хоп.** Весь `/api/*` и `/auth/*` идёт `Caddy → Next (Node) → api
(Node)` через `rewrites` в `next.config.ts`. То есть каждый из 100–150 req/s проходит
через **второй однопоточный Node-процесс**, который в то же время рендерит страницы.
`proxy.ts` к этим маршрутам не применяется вовсе — его `matcher` их исключает
(`src/proxy.ts`, `config.matcher`), так что Next здесь работает чистым прокси.

## Вывод по масштабированию: вертикально + одна развилка ролей

**Горизонтальное масштабирование (несколько машин, балансировщик, общий кэш) для 1000
онлайн не нужно и не окупается.** После починки находок группы A стоимость запроса
падает до 1–3 мс, и один процесс отдаёт 300+ req/s при целевых 150. Данных — единицы
гигабайт, они целиком влезают в память одного сервера.

Но **однопроцессная схема «всё в одном `node dist/main`» должна кончиться**, и не
ради масштабирования, а ради изоляции: сегодня десятиминутный обход синка и
двухсекундный сброс трекера активности воруют event loop у торгового интерфейса. Нужна
ровно одна развилка:

- **`api`** — N одинаковых HTTP-воркеров, **без единого `setInterval`**, без
  telegram-поллинга. Их можно запускать хоть в `cluster`, хоть N контейнерами — они
  ничего не помнят между запросами.
- **`worker`** — **ровно один** процесс: все фоновые циклы (`trade-sync`,
  `balance-snapshot`, `price-sync`, `liquidity-snapshot`, `market-alerts`,
  `weekly-report`, `usage-tracker` flush, `tron-watcher`) и telegram `getUpdates`.

Разводится переменной окружения (`ROLE=api|worker|all`, `all` — дефолт для локального
запуска). Это ~50 строк в `app.module.ts` и `main.ts`, и она снимает **все** названные
блокеры горизонтального роста разом: in-memory `inFlight`-локи, TTL-кэши, счётчик
`syncFailures`, требование «один поллер бота на токен» — всё это перестаёт быть
проблемой, потому что живёт в единственном процессе по определению, а не по удаче.

Почему это стоит своей сложности именно здесь: цена — один `if` по переменной окружения
и одна лишняя строка в compose. Цена альтернативы («оставить как есть») — что любое
добавление второго HTTP-воркера в будущем требует Redis, распределённых локов и выборов
лидера. Разделение ролей покупает эту возможность заранее почти бесплатно и **сегодня же**
даёт главное: тяжёлый фон не трогает интерфейс.

### Оценка железа

| Ресурс | Сегодня | Нужно под 1000 онлайн после правок |
|---|---|---|
| vCPU | ? | **4–8** (2–4 `api`-воркера + 1 `worker` + Postgres) |
| RAM | ? | **8–16 ГБ** (Postgres `shared_buffers` 2 ГБ + рабочий набор) |
| Диск | ? | **100 ГБ SSD**, из них `user_activity_minutes` — главный потребитель, см. A8 |
| Исходящие HTTPS | — | ~35/с к биржам (по ключу пользователя, лимиты у бирж на UID — не на IP) |

## Находки

### A. Чинить обязательно под 1000 онлайн

#### A1. Агрегаты «Обзора» читают всю историю с колонкой `raw` и делают это заново каждые 60 секунд

`backend/src/trades/trades.service.ts:140` (`list`), `:426` (`statsByTag`), `:551`
(`statsByTagCombo`), `:715` (`statsByTime`), `:782` (`stats`);
`backend/src/trades/trade-rows.ts:90` (`loadRows` — общий для `lab` и `habits`).

Ни один из этих `findMany` не задаёт `select`, поэтому Prisma тянет все скалярные поля,
включая `Trade.raw Json?`. Все поля, которые аггрегаты реально читают, перечислены в
`positions.ts:82` (`TradeRowLike`) — `raw` там нет и не было.

Что ломает: 50 таких запросов в секунду × 900 строк = 45 000 строк/с и ~20 МБ/с
разбираемого и выбрасываемого JSON. Плюс `list` (`:140`) грузит **всю** историю, чтобы
отдать 20 строк страницы — постраничность считается после схлопывания в позиции, и это
верное решение (см. комментарий на `:137`), но оно не обязано означать «прочитать всё
из базы».

Починка — три слоя, по возрастанию пользы:
1. `select` вместо неявного «всё» во всех шести местах. Механически, поведение не
   меняется, читаемых байт становится в 5–10 раз меньше.
2. Версия данных пользователя + memo-кэш ответа (A2) — снимает 95% этих запросов вовсе.
3. `equity` прореживать на сервере: фронт рисует
   `buildEquityGeometry(equity, 300)` (`views/overview/Page.tsx:56`) — то есть **всё,
   что длиннее ~600 точек, он выбрасывает**, а сервер шлёт хоть 5000. У спарклайнов
   тегов прореживание уже есть (`thinEquity`, `trades.service.ts:97`); у главной кривой
   его нет.

#### A2. Один и тот же ответ считается заново 60 раз в час на неизменившихся данных

Те же файлы. Данные сделок меняются только когда синк что-то вставил — то есть в
худшем случае раз в минуту, а обычно раз в несколько часов. Между вставками
`stats(userId, days=30)` — чистая функция.

Починка: счётчик версии данных на пользователя (bump при вставке сделок, при правке
тегов, при пересчёте контекста) + LRU-кэш ответов в памяти процесса, ключ
`(userId, version, params)`. Оттуда же берётся `ETag: W/"<version>:<hash params>"`, и
шестидесятисекундный повторный запрос вкладки превращается в **304 с пустым телом** —
пропадает и CPU, и трафик.

Размер: одна запись ответа `stats` после прореживания `equity` — ~30 КБ. Тысяча
пользователей × 4 комбинации параметров = ~120 МБ; LRU с потолком (например, 5000
записей) держит это в рамках. Кэш в памяти процесса, не в Redis — см. раздел C1.

#### A3. Цикл синхронизации последовательный и дублирует вызовы биржи

`backend/src/trades/trade-sync.service.ts:79–93` — `for` по пользователям, внутри
`await` на сеть.
`backend/src/trades/trade-sync.service.ts:198` и
`backend/src/trades/position-builder.service.ts:80` — **два одинаковых
`adapter.getOpenPositions(creds)` в одном тике одного пользователя**.
`backend/src/balance/balance-snapshot.service.ts:69–89` — тот же последовательный
шаблон раз в час.

Что ломает: при 250 мс на вызов и четырёх вызовах на пользователя обход укладывается в
минуту примерно до **60 подключённых аккаунтов**. На 1000 подключённых один обход —
около десяти минут, `sweeping` глотает девять тиков из десяти.

Починка:
- ограничитель параллелизма на обходе (8–16 одновременных пользователей; это ~50 с на
  1000 аккаунтов при 12 в параллель — помещается в интервал). Ограничитель, а не
  `Promise.all`: тысяча одновременных исходящих HTTPS и тысяча параллельных транзакций
  положат и пул Prisma, и сеть;
- открытые позиции запрашивать один раз за тик и передавать в `PositionBuilderService`
  параметром;
- считать и логировать длительность обхода — без этого «разъехался или нет» не видно.

#### A4. `PositionBuilderService.rebuild` перечитывает всю историю исполнений каждую минуту

`backend/src/trades/position-builder.service.ts:178` (все `executions` пользователя),
`:225` (все `trades` пользователя), `:233` (`update` построчно).

Запускается из каждого тика синка, **независимо от того, пришло ли что-то новое**.
2000 филлов + 900 сделок = 2900 строк на пользователя в минуту; при 1000 подключённых —
**2.9 млн строк в минуту**, около 48 000 строк/с, только ради того, чтобы почти всегда
ничего не изменить (комментарий на `:224` честно говорит «steady-state tick writes
nothing» — но читает при этом всё).

Починка: не перестраивать, когда `fetchAndStoreExecutions` вернул 0 новых филлов и
открытые позиции не изменились; при перестройке ограничивать обход символами, которых
коснулись новые филлы, и временем от начала самой ранней незакрытой позиции. Позиция,
закрывшаяся полгода назад, не может получить другой `positionId` — перечитывать её
филлы незачем.

#### A5. `TradeRiskService.computeMissing` — безлимитный N+1 внутри часового цикла

`backend/src/balance/trade-risk.service.ts:63` — `findMany` **без `take`** (сравнить с
`TradeContextService`, где стоит `BATCH_LIMIT = 400`, `trade-context.service.ts:288`);
`:85` — `history.balanceAt` на **каждую** сделку;
`backend/src/balance/balance-history.service.ts:28` — `balanceAt` читает **все** якоря
баланса пользователя, плюс `loadFlows` двумя запросами.

Что ломает: у пользователя с годом истории якорей 8760, сделок без метрик — 900. Один
прогон = 900 × (8760 строк + 2 запроса) ≈ **7.9 млн строк и 2700 запросов на одного
человека**, и всё это внутри последовательного часового обхода всех пользователей.
На 1000 подключённых часовой цикл не закончится никогда.

Починка: `take` как у контекста; якоря читать один раз на пользователя и передавать в
`balanceAt`; `tradeRisk.create` заменить на `createMany` пачкой.

#### A6. Рыночные эндпоинты ходят во внешние API на каждый запрос каждого пользователя

`backend/src/analytics/analytics.service.ts:53` (`getMarketData` → CoinGecko), `:69`
(`getCMC20` → CMC/CoinGecko), `:120` (`getFearAndGreed` → alternative.me), `:136`
(`getDeFiTVL` → DeFiLlama, ответ в сотни КБ), `:169` (`getLongShortRatio` → три запроса
к Bybit), `:156` (`getLiquidityHistory` → до 5000 строк из БД).
Кэш есть **только** у `getVolatility` (`:250`).

Ответ у всех семи **одинаков для всех пользователей**. Стоимость раздела «Рынок» растёт
линейно по числу зрителей без всякой причины, и на сотнях активных упирается в чужие
лимиты (бесплатный CoinGecko — десятки запросов в минуту) раньше, чем в свои.

**Это не новая находка.** Она уже разобрана и спроектирована в
`docs/superpowers/specs/2026-09-02-data-warmup-design.md`, раздел «Предусловие: кэш
внешних данных „Рынка“» — с TTL по каждому эндпоинту и с обоснованием, почему кэш в
памяти процесса, а не в Redis. В коде эта часть спеки **не реализована**. Задача здесь —
исполнить её как написано, а не проектировать заново.

#### A7. `market-events` пересчитывает 17 520 свечей на каждый запрос

`backend/src/market-events/market-events.service.ts:66` (`getHourlyStats`), `:102`
(`getWeekdayHourStats`) — оба читают два года часовых свечей (`days = 730` по
умолчанию) и проходят их циклом; `:37` (`getCorrelation`) — 730 дневных.

Результат глобальный (BTC один на всех) и меняется **раз в час**, когда синк свечей
кладёт новую строку. При этом `getWeekdayHourStats` зовётся ещё и из `market-alerts`
каждые пять минут (`market-alerts.service.ts:290`).

Один вызов — 17 520 строк из Postgres, ~3–5 МБ аллокаций и 60–120 мс блокирующего
цикла. Даже один запрос в секунду — это 10% ядра на пересчёт неизменившегося числа.

Починка: кэш с TTL 1 час по ключу `(метрика, days)` в том же стиле, что A6. Дальше —
если понадобится — считать в `worker` сразу после `PriceSyncService`, но TTL хватает.

#### A8. `user_activity_minutes` — самая быстрорастущая таблица продукта, и у неё нет ни срока жизни, ни нормального ключа

`backend/prisma/schema.prisma:611–623`.

Строка на пользователя на минуту. Фоновая вкладка опрашивает API сама (это прямо
сказано в комментарии к модели), значит **у открытой вкладки активна каждая минута**.

- реалистично (4 часа присутствия в сутки): 1000 × 240 = 240 тыс. строк/сутки →
  **87 млн строк/год**;
- вкладка оставлена открытой: 1000 × 1440 = 1.44 млн строк/сутки → **525 млн/год**.

Стоимость строки: `id` — `String @default(uuid())`, то есть в Postgres это `text` на
37 байт, плюс `userId` тоже `text` 37 байт, плюс **четыре** индекса, из которых
`@@index([userId, minute])` (`:621`) **полностью дублирует** `@@unique([userId, minute])`
(`:619`) — одинаковый порядок колонок, одинаковая польза, двойная цена на каждой
вставке. Итого ~315 байт на строку → **27 ГБ в год** в реалистичном сценарии и
**165 ГБ** в пессимистичном.

Плюс два запроса админки сканируют таблицу целиком без ограничения по времени:
`admin/usage/usage-queries.ts:166` (`countReturningUsers`) и `:187` (`queryActiveWeeks`).
На 87 млн строк это минуты seq-скана, выбитый кэш Postgres и занятое соединение — то
есть один заход владельца в админку тормозит всех.

Починка:
- составной первичный ключ `@@id([userId, minute])` вместо `id uuid` — ровно тот приём и
  ровно то обоснование, что уже записаны в схеме для `PriceCandle`
  (`schema.prisma:545–551`). Убирает 37 байт данных и целый индекс с самой растущей
  таблицы. То же для `UserSectionDay` (`@@id([userId, day, section])`);
- снести дубли индексов (см. A9);
- сметатель старых минут (например, 180 дней) в `worker`, по образцу
  `RefreshTokenCleanupService`;
- `countReturningUsers` и `queryActiveWeeks` ограничить окном отчёта.

#### A9. Пул соединений Prisma и настройки Postgres — дефолтные

`DATABASE_URL` в `docker-compose.prod.yml` (строка `DATABASE_URL: postgresql://...`)
не содержит `connection_limit`, то есть Prisma берёт `num_cpus * 2 + 1` — на 4-vCPU
машине **девять** соединений при ~680 запросах в секунду, часть которых держит
соединение десятками миллисекунд. Образ `postgres:16-alpine` поднимается без единого
`-c`, то есть с `shared_buffers = 128 МБ` и `work_mem = 4 МБ`.

Плюс четыре **полностью избыточных** индекса (каждый — лишняя запись на каждой вставке,
а вставки идут пачками на бэкфилле):

| Избыточный | Перекрывается | Файл |
|---|---|---|
| `user_activity_minutes @@index([userId, minute])` | `@@unique([userId, minute])` | `schema.prisma:621` |
| `balance_snapshots @@index([userId, exchange, at])` | `@@unique([userId, exchange, at])` | `schema.prisma:659` |
| `trades @@index([userId, exchange])` | префикс `@@unique([userId, exchange, orderId, closedAt])` | `schema.prisma:156` |
| `executions @@index([userId, exchange])` | префикс `@@unique([userId, exchange, execId, orderId])` | `schema.prisma:191` |

Починка: явный `connection_limit` под роль процесса (`api` — 10 на воркер, `worker` —
10), `pool_timeout`; Postgres через `command: postgres -c shared_buffers=2GB -c
effective_cache_size=6GB -c work_mem=16MB -c random_page_cost=1.1 -c max_connections=100`;
индексы-дубли снести.

#### A10. Каждый запрос к API проходит через лишний Node-процесс

`frontend/next.config.ts` (`rewrites`), `docker-compose.prod.yml` (наружу смотрит только
`caddy` → `web`), `deploy/Caddyfile` (единственный `reverse_proxy web:8090`).

100–150 req/s буферизуются и переотправляются Next-сервером, который в это же время
рендерит страницы. При этом `src/proxy.ts` к `/api/` и `/auth/` **не применяется** — его
`matcher` их прямо исключает, то есть Next на этих маршрутах не делает ничего, кроме
перекладывания байтов.

Починка: разложить маршруты в Caddy:

```
{$APP_DOMAIN} {
	encode zstd gzip
	handle /api/* { reverse_proxy api:8091 }
	handle /auth/* { reverse_proxy api:8091 }
	handle { reverse_proxy web:8090 }
}
```

**Инвариант продукта при этом не нарушается** — см. раздел «Решения, которые нельзя
менять не обсудив», пункт 1: origin остаётся ОДИН (то же имя хоста, та же кука с
`path: '/'`), меняется только то, какой контейнер внутри сети отвечает на префикс.
`rewrites` в `next.config.ts` **остаются** — они нужны локальному запуску без Caddy.

### B. Стоит сделать заодно — но не блокер

#### B1. Рыночные сигналы: четыре запроса в БД на пользователя на сигнал

`backend/src/notifications/notifier.service.ts` — `thresholdFor` зовёт `prefs.get`
(`user.findUnique`), `maybeSend` зовёт `prefs.get` **ещё раз**, `state.check`
(`notification-state.service.ts`) делает `findUnique` + `upsert`.
`backend/src/notifications/market-alerts.service.ts:115–124` — цикл по пользователям на
каждый из семи сигналов.

При этом `MarketAlertsService.tick` **уже загрузил настройки всех пользователей одним
запросом** (`prefs.linkedUsers()`, `prefs.service.ts`) — и выбрасывает их, чтобы
`notifier` перечитал те же строки по одной.

1000 привязанных чатов × 7 сигналов × 4 запроса = 28 000 запросов за тик, тик каждые
5 минут → **93 q/s** в ровном режиме, всё последовательно (то есть тик ещё и не
укладывается в интервал). Отдельно: `volatileHour` вне окна (`:278`) делает `maybeSend`
на каждого пользователя ради снятия фронта — это минимум 2 запроса на человека каждые
пять минут при заведомо ложном условии.

Починка: пробрасывать уже загруженные `prefs` в `notifier` параметром; состояния
сигналов читать одним `findMany` по `(userId in […], key in […])` на тик и писать
пачкой; «снятие фронта» делать одним `updateMany` по множеству, а не по одному.

#### B2. Сброс трекера активности — последовательные upsert'ы

`backend/src/admin/usage/usage-tracker.service.ts:134–143` (`for` с `await`), `:160–189`
(`upsert` на минуту + `upsert` на каждый раздел).

При 1000 онлайн каждый сброс (раз в 30 с) разбирает 500–1000 корзин × ~2.5 upsert'а =
до 2500 последовательных round-trip'ов ≈ **2–4 секунды event loop каждые 30 секунд**.

Починка: один `$executeRaw` с многострочным `INSERT ... ON CONFLICT DO UPDATE SET
requests = table.requests + EXCLUDED.requests` на всю пачку. Семантика инкремента
сохраняется, round-trip становится один.

Отдельно: `MAX_BUFFERED_MINUTES = 20 000` (`:18`) при 1000 онлайн достигается за
20 минут простоя БД, а не «только в патологии», как говорит комментарий. Порог стоит
пересчитать от целевого числа онлайн (1000 онлайн × 1 минута × запас), а не оставлять
как есть.

#### B3. `TradeContextService.computeMissing` делает три запроса на пустом месте

`backend/src/trades/trade-context.service.ts:283` (`dropStale` — `findMany` по
`trade_contexts` с фильтром через связь), `:285` (`trade.findMany({ context: null })`),
`:330` (то же для качества).

Три запроса на пользователя каждую минуту, чтобы почти всегда получить пустой список.
`dropStale` при этом полезен ровно после поднятия `CTX_VERSION`, а не ежеминутно.

Починка: пропускать целиком, если синк ничего не вставил и версия контекста не менялась
с прошлого тика (флаг в памяти `worker`-процесса — он теперь единственный).

#### B4. Чтение кредов — два запроса на каждый поллинг позиций

`backend/src/credentials/credentials.service.ts` (`activeExchange` + `get`), зовётся из
`exchanges/exchange.controller.ts:29` (`/api/exchange/positions`, 2 раза в минуту на
вкладку) и из каждого тика синка.

1000 онлайн → 66 q/s только за креды. Плюс 33 исходящих HTTPS в секунду к биржам, из
которых часть — дубли от нескольких вкладок одного человека.

Починка: короткий кэш кредов в памяти (30–60 с, сброс при правке ключей в
`settings.controller`) и **коалесинг** ответа `getOpenPositions` на 10–15 секунд по
`userId` — ровно тот приём, который уже написан в
`bybit/services/bybit-market.service.ts:19` (`cached` + `inflight`). Две вкладки одного
человека перестают быть двумя запросами к бирже.

#### B5. `/api/market-data/candles` по умолчанию отдаёт 5000 строк

`backend/src/market-data/market-data.controller.ts` (`MAX_LIMIT = 5000` и он же дефолт
при отсутствии `limit`). Реплей бектеста берёт минутки кусками по 5000
(`views/backtest/model/useReplay.ts:24`) — ~500 КБ JSON и 15–30 мс сериализации на кусок.
При сотне одновременных сессий это терпимо, но дефолт в 5000 для запроса **без** `limit`
— это приглашение к случайному тяжёлому запросу.

Починка: дефолт (без `limit`) снизить до 500; `MAX_LIMIT` оставить как потолок явного
запроса. Свечи неизменяемы — добавить `Cache-Control: public, max-age=86400,
immutable` для окон, целиком лежащих в прошлом: тогда повторный проход по тем же
минуткам вообще не доходит до Node.

#### B6. Курсор сессии бектеста пишется раз в 3 секунды

`views/backtest/model/useReplay.ts:32` (`SAVE_EVERY_MS = 3000`) →
`backtest.service.ts:160` (`advance`: `findUnique` + `update`).
Сто одновременных реплеев — 33 записи/с и ~66 запросов/с. Само по себе не страшно, но
это единственный постоянный поток **записи** от интерфейса.

Починка: поднять интервал до 10 с и сохранять по `visibilitychange`/уходу со страницы
(`keepalive` уже есть). Потеря точности — до десяти секунд симуляции, что в бектесте
незаметно.

#### B7. `/api/trades/habits` — самый дорогой эндпоинт продукта, и он сейчас отключён на фронте

`backend/src/trades/habits.service.ts:37` (`PERM_ITERS = 2000`), `:207` (перестановочный
тест на каждый кандидат), `:185` (`loadRows` — вся история).
`frontend/src/views/overview/Page.tsx:45` — вызов **закомментирован**, но хук
`useHabits` (`entities/trade/api/hooks.ts:103`) наследует `LIVE`, то есть
`refetchInterval: 60_000`.

Тридцать–шестьдесят гипотез × 2000 перестановок × длина среза — это сотни миллисекунд
чистого синхронного CPU на запрос. Если блок «Цены привычек» вернут на «Обзор» **до**
задачи A2, тысяча онлайн даст ~17 таких запросов в секунду — это в одиночку кладёт
процесс.

Починка: не трогать сам алгоритм (число перестановок — вопрос статистической честности,
не производительности), но обязать этот эндпоинт версионным кэшем из A2 и снять с него
`refetchInterval` вовсе: привычки за минуту не меняются.

#### B8. Мелочи процесса

- `backend/src/main.ts` — нет `app.enableShutdownHooks()`. Значит на `SIGTERM`
  `onModuleDestroy` **не вызывается**, и финальный сброс `UsageTrackerService`
  (`usage-tracker.service.ts:61`, написанный специально ради этого) не срабатывает при
  каждом деплое.
- `backend/src/main.ts` — не заданы `server.keepAliveTimeout` / `headersTimeout`. Дефолт
  Node — 5 секунд; за обратным прокси это штатная причина спорадических 502 под
  нагрузкой. Ставить 65 с / 66 с.
- Нет `/health`-эндпоинта, хотя `admin/usage/sections.ts` его уже исключает из учёта, а
  `docker-compose.prod.yml` не имеет `healthcheck` у `api` и `web`.
- `bybit/services/bybit-market.service.ts:14` — записи кэша никогда не удаляются по
  истечении TTL, только перезаписываются. Ключей конечное число (символ × интервал), так
  что утечки нет, но памяти это стоит десятки мегабайт; периодическая чистка просроченных
  — три строки.
- `docker-compose.prod.yml` — у контейнеров нет `deploy.resources.limits`. Один
  разогнавшийся `worker` может выесть память у Postgres на той же машине.

### C. Overkill для этого масштаба — и почему

#### C1. Redis

**Не нужен.** Кэшировать надо две вещи: (а) рыночные данные, общие для всех, и (б)
агрегаты, свои у каждого пользователя.

Для (а) хватает `Map` в памяти: при 2–4 `api`-воркерах и TTL 10 минут получается
4 внешних вызова на 10 минут вместо одного — по-прежнему в десятки раз ниже любого
бесплатного лимита. Для (б) правильный ответ — не кэш, а версия данных: она живёт в
Postgres, где и так лежат сами данные, и не требует второго источника правды.

Redis здесь — это ещё один stateful-сервис, который соло-разработчику придётся
мониторить, обновлять и отлаживать, ради экономии трёх внешних HTTP-вызовов в час.
Порог, за которым он окупается: несколько **хостов** (не воркеров), то есть когда одной
машины перестанет хватать — а это, по оценке выше, далеко за 1000 онлайн.

#### C2. BullMQ / очередь задач

**Не нужна.** Единственное место, похожее на очередь, — веерный обход пользователей в
синке. Ему нужен ограничитель параллелизма (десяток строк), а не брокер: задачи
однородные, идемпотентные, без приоритетов, без ретраев с бэкоффом (следующий тик через
минуту и есть ретрай) и без необходимости переживать перезапуск (курсор — состояние БД,
а не очереди).

Порог, за которым очередь окупается: когда обход не помещается в интервал даже при
параллелизме 16, то есть примерно **5000+ подключённых аккаунтов**, или когда появятся
задачи с разными приоритетами и длительностями (ре-бэкфилл истории по требованию).
Тогда первым шагом будет не BullMQ, а шардирование по `hash(userId) % N` между
несколькими `worker`-процессами — оно дешевле и не добавляет Redis.

#### C3. WebSocket вместо поллинга

**Не окупается.** После A1/A2 повторный опрос стоит один 304-ответ (~1 мс, пустое тело).
Экономия от WebSocket — эта миллисекунда, а цена — 1000 постоянных соединений, которые
надо держать в `api`-воркерах, плюс шина от `worker` к ним, чтобы было чем пушить, — то
есть Redis pub/sub, который мы только что отказались заводить.

Отдельно: свежее 30 секунд позиции всё равно не станут — их источник это REST биржи с
её же лимитами. Порог для пересмотра: ≥5000 онлайн либо требование к обновлению
позиций чаще 5 секунд.

#### C4. Разделение БД, реплики чтения, партиционирование

**Не нужны** при единицах гигабайт. Единственная таблица, которая когда-нибудь заслужит
партиционирование по времени, — `user_activity_minutes`, и до этого её сначала надо
привести в порядок (A8): составной ключ плюс срок жизни в 180 дней удерживают её в
пределах, где обычный btree справляется.

#### C5. Перевод всех `String @default(uuid())` в `@db.Uuid`

Экономия реальная (37 байт текста против 16 байт `uuid` в каждом ключе и каждом
внешнем ключе), но в проекте **нет миграций** — схема синхронизируется `db push`, и
смена типа колонки означает переписывание таблиц с приведением типов на живых данных.
Цена ошибки несопоставима с выигрышем. Вынесено в «нельзя менять не обсудив».

## Решения, которые нельзя менять не обсудив

Оптимизация в нескольких местах подходит вплотную к уже зафиксированным решениям
продукта. Ни одно из них здесь не нарушается — но проверить это должен владелец, а не
исполнитель задачи.

1. **«Домен ведёт на Next, а не отдельно на API» (`CLAUDE.md`, «Стек и структура»).**
   Задача T9 переносит маршрутизацию `/api/*` и `/auth/*` из `rewrites` Next в Caddy.
   Смысл правила — **один origin**, потому что куку сессии ставит backend, а читает её
   `proxy.ts` на стороне Next. После T9 origin остаётся ровно один: то же имя хоста, тот
   же `path: '/'` у куки, тот же `FRONTEND_URL` и та же настройка CORS; меняется только
   то, какой контейнер **внутри** сети compose отвечает на префикс. Отдельного домена
   для API не появляется, и появиться не должно. Формулировку в `CLAUDE.md` после T9
   надо уточнить — «один origin», а не «через Next», — иначе следующий читатель
   откатит правку как нарушение.

2. **«Опрос бота живёт ровно в одном окружении» (`CLAUDE.md`, «Уведомления в
   Telegram»).** T11 не ослабляет это правило, а усиливает: поллинг регистрируется
   только в роли `worker`, и `worker` в compose один. Но из этого следует запрет:
   **`worker` нельзя масштабировать `--scale`**, и в `docker-compose.prod.yml` это надо
   написать комментарием рядом с сервисом, а не держать в голове. Если когда-нибудь
   понадобится второй `worker`, сначала — шардирование по `hash(userId)`, и бот остаётся
   на шарде 0.

3. **«Фандинг не подмешивается в `Trade.closedPnl`», «PnL по тегам не делится между
   тегами», «таймфрейм — поле, а не тег» (`CLAUDE.md`).** Ни одна задача этой спеки их
   не задевает. Важно, что **T2 и T10 обязаны быть бит-в-бит нейтральны по числам**: если
   после `select` или после кэша хоть одна метрика изменилась, это баг задачи, а не
   «уточнение расчёта». Приёмка T2/T10 — сравнение полного ответа всех аггрегатов на
   демо-аккаунте до и после.

4. **Смена первичного ключа `user_activity_minutes` / `user_section_days` (T18) — это
   операция с данными, а в проекте нет миграций.** Схема синхронизируется `db push`, и
   снятие колонки `id` потребует разового `--accept-data-loss` на проде — ровно того,
   чего `docker-compose.prod.yml` избегает намеренно (комментарий у `command` сервиса
   `api`). Данные при этом аналитические и восстановлению не подлежат. Решение владельца:
   (а) пойти на разовую потерю/пересоздание таблиц, (б) сохранить историю дампом и
   залить обратно, или (в) ограничиться сроком жизни и снятием дубля индекса, оставив
   `id` как есть. **По умолчанию исполнителю: вариант (в)**, пока владелец не сказал
   иначе.

5. **Перевод всех `String @default(uuid())` в `@db.Uuid`** (раздел C5) — соблазнительная
   экономия, требующая переписывания всех таблиц с приведением типов на живых данных без
   миграций. **Не делать.**

6. **`MIN_SEGMENT`, `PERM_ITERS`, `MIN_SQN_POSITIONS`, `CTX_VERSION`, `RISK_VERSION`,
   `BACKFILL_WEEKS` — не ручки производительности.** Это пороги статистической честности
   и полноты данных; часть из них, по `CLAUDE.md`, ещё и завязана на числа витрины
   демо-аккаунта (Edge Score 53 при `DEFAULT_DAYS = 30`). Ускоряться за их счёт нельзя:
   правка любого из них меняет **то, что продукт утверждает**, а не то, как быстро он это
   считает.

7. **`Trade.raw` не удалять.** T2 перестаёт его **читать** в аггрегатах — это всё. Сама
   колонка нужна для forward-compat (комментарий к модели `Trade`), и вопрос «а не
   выбросить ли её вовсе» — отдельный разговор с владельцем, не побочный эффект
   оптимизации.

## Открытые вопросы к владельцу

1. **Срок жизни `user_activity_minutes`.** 180 дней достаточно для отчётов админки
   («визиты», «дни с активностью», «удержание по когортам»)? Когортное удержание за
   более длинный горизонт после сметания придётся считать по свёрнутым суткам, а не по
   минутам.
2. **Где сбрасывать буфер активности после T11.** Интерсептор считает запросы в
   `api`-воркерах; если сброс оставить там, каждый воркер сбрасывает свою пачку (upsert
   с инкрементом это переживёт — конфликтов нет, но round-trip'ов станет N×). Если
   вынести в `worker` — нужен канал от `api` к `worker`, то есть тот самый Redis,
   которого мы избегаем. Предлагаемый ответ: **оставить сброс в `api`-воркерах**, он
   идемпотентен по конструкции и после T16 стоит один запрос на воркер.
3. **Пункт 4 раздела выше** — вариант (а), (б) или (в) для ключа таблиц активности.
4. **Целевая машина.** Оценка «4–8 vCPU / 8–16 ГБ / 100 ГБ SSD» сделана из расчётных
   чисел. Какой VPS стоит сейчас — это определяет, нужна ли вертикальная миграция до
   начала работ или после.
