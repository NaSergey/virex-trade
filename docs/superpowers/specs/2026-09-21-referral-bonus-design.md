# Реферальный бонус: 1000 монет за приглашённого

Дата: 2026-09-21

## Задача

Дополняет `docs/superpowers/specs/2026-09-07-referral-invites-design.md`: инфраструктура
рефералки (`invitedById`, кастомный слаг, статистика `total`/`withKey`) есть, вознаграждения
нет. Начисляем пригласившему 1000 монет **в момент регистрации** приглашённого — по факту
регистрации, а не по факту активности (подключения ключа биржи и т. п.), как явно
сформулировано в задаче.

## Начисление

- Новый вид `CoinTxKind = 'REFERRAL_BONUS'` (`backend/src/coins/coins.service.ts`) + строка
  в дублирующем doc-комментарии `schema.prisma` рядом с остальными видами.
- Сумма — константа `REFERRAL_BONUS_COINS = 1000` в `backend/src/coins/coins.config.ts`,
  рядом с `STARTING_COINS`/`COINS_PER_USDT`: тот же принцип — константа кода, не переменная
  окружения и не магическое число по месту вызова.
- `AuthService.register()`: `user.create` и (если `invitedById` резолвится) `coins.credit(tx,
  invitedById, REFERRAL_BONUS_COINS, 'REFERRAL_BONUS', user.id)` — в одной `$transaction`.
  Атомарно с созданием пользователя по тому же принципу, что у доната и турнира: начисление не
  должно разойтись с событием, которое его вызвало. Создание стартовых тегов
  (`TagsService.createDefaults`) остаётся отдельным try/catch **после** транзакции, как сейчас
  — это не денежная операция, откатывать регистрацию из-за нее нельзя.
- Идемпотентность — существующий индекс `coin_tx_once (userId, kind, refId)`:
  `refId = <id нового пользователя>`. Одно начисление на одну регистрацию гарантирует индекс
  БД, а не проверка в коде.
- `AuthModule` импортирует `CoinsModule` (сейчас не импортирует — инжектируем `CoinsService`
  в `AuthService`).

## Сознательно не делаем

- **Не начисляем задним числом** по уже существующим связям `invitedById` без бонуса —
  решение владельца продукта: бонус только для регистраций с этого релиза.
- **Не добавляем поле «заработано монет» в `ReferralsService.getStats`.** Начисление видно в
  истории монет пользователя; фронт вообще не показывает историю транзакций монет ни для
  одного вида (`TOURNAMENT_PRIZE` и другие тоже не размечены в UI), значит `REFERRAL_BONUS`
  и не должен становиться первым исключением без отдельного запроса.

## Фронтенд

- `ReferralDialog` (`referrals.lede`, `frontend/src/shared/i18n/messages/ru.json` и
  `en.json`) — текст меняется на явное упоминание бонуса: сейчас реферальная ссылка выглядит
  как техническая функция «кто кого привёл», а с деньгами на кону подпись обязана сказать,
  зачем её посылать другу.

## Известный риск (осознанно не закрываем)

Прошлый дизайн-документ (2026-09-07) отдельно отложил вопрос злоупотреблений «до появления
вознаграждения» — теперь оно появилось. Ничего не мешает завести второй аккаунт и
зарегистрироваться по собственной ссылке ради 1000 монет. Урон ограничен тем, что монеты
нельзя ни вывести, ни передать другому игроку (см. «Игры и внутренняя валюта» в CLAUDE.md):
предельный случай — раздутый игровой баланс на собственных фейковых аккаунтах, не украденные
деньги. Для первой версии это приемлемо. Если понадобится ограничение (например, начислять по
`withKey`, а не по `total`, — то есть по факту подключения ключа биржи, а не голой
регистрации), это отдельный дизайн с явным продуктовым решением, а не тихая правка сейчас.

## Тестирование

`backend/src/auth/auth.service.spec.ts`: конструктор `AuthService` получает четвёртый
аргумент (`CoinsService`), мок `prisma` получает `$transaction`, вызывающую колбэк с тем же
стабом. Новые проверки: валидный `ref` начисляет `REFERRAL_BONUS_COINS` пригласившему (мок
`coins.credit` — spy, проверяются все пять аргументов, включая `refId = id нового
пользователя`); без `ref` и с несуществующим `ref` — `credit` не вызывается. Четыре
существующих теста обновляются под новую сигнатуру конструктора без изменения проверяемого
поведения.
