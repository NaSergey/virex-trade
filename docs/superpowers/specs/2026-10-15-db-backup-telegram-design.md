# Бэкап базы в Telegram раз в неделю

Запрос владельца 2026-10-15: раз в неделю снимать базу и присылать файлом через бота
(@Trade_play_bot) ему в Telegram; на сервере файлы не копятся. Только данные
пользователей — рыночные данные BTC не нужны.

## Что входит в бэкап

`pg_dump --format=custom` всей базы, **кроме данных рыночных таблиц** —
`price_candles` (свечи BTC, ~967 МБ из ~983 МБ базы на 2026-10-15) и
`liquidity_snapshots` (снимки стакана BTC). Их структура в дампе есть
(`--exclude-table-data`, а не `--exclude-table`): восстановленная база
поднимается той же схемой, свечи синк дольёт с Binance сам (на пустой таблице
он идёт от 2018 года, около получаса). Всё остальное — пользователи, сделки,
теги, сессии, монеты, игры — целиком. Замер на проде: ~1 МБ сжатого дампа.

## Где и когда

- Сервис `DbBackupService` (`backend/src/backup`) в роли `worker` — фоновый, как
  остальные, guard'ом `runsBackgroundJobs()`.
- **Включается переменной `DB_BACKUP_TELEGRAM=1`, и она стоит только у `worker`
  в `docker-compose.prod.yml`** — прямо в файле, не в `.env.prod`, забыть её
  нечем. Локальный запуск (`ROLE=all`) бэкап не шлёт: иначе база разработчика
  уезжала бы в тот же чат, что и прод (та же история, что с дублями
  уведомлений).
- **Слот — понедельник 00:00 UTC (03:00 МСК).** Сервис проверяет раз в час (и
  на старте): если с последнего слота отправленного бэкапа нет — снимает и
  шлёт. Отсюда: пропущенный слот (worker лежал) догоняется, как только он
  поднялся; перезапуск не шлёт второй раз; **первый бэкап уходит сразу после
  деплоя** — это и проверка, что всё работает.
- Отправленные бэкапы — строки `db_backups` (`sentAt`, `bytes`, `parts`):
  последняя — точка отсчёта недели. Только в памяти процесса её держать
  нельзя — перезапуск `worker` слал бы бэкап заново.

## Кому

Владельцу: аккаунт `OWNER_EMAIL` (`admin/owner.ts`) и его привязанный к боту
чат (`User.telegramChatId`). Bot API не пишет человеку по `@username` — только
по id чата, а id появляется, когда человек привязал Telegram в настройках.
Получатель зашит кодом, как и доступ к админке: отдельной переменной с id
чата, которую можно выставить не туда, нет. Чат не привязан — бэкап не
снимается, в лог предупреждение, повтор через час.

## Файлы не копятся

Дамп пишется во временный каталог процесса и удаляется в `finally` при любом
исходе. На сервере не остаётся ничего. В чате — одно сообщение в неделю;
удалить старые бот не может (Bot API удаляет сообщения не старше 48 часов).

## Отправка

`sendDocument` с файлом `trade-play-YYYY-MM-DD.dump` и подписью: дата, размер,
команда восстановления, оговорка про свечи. Лимит Bot API на файл — 50 МБ;
дамп больше 45 МБ режется на части `….dump.part01`, `part02`… (номер с нулём —
`cat ….part*` склеивает их в правильном порядке), каждая — своим сообщением.

## Ошибки

- `pg_dump` упал или Telegram не принял файл — строки нет, повтор через час.
  Владельцу один раз за слот уходит текст «бэкап не снят» с причиной: молча
  сломанный бэкап хуже, чем отсутствующий.
- Пароль базы передаётся `pg_dump` переменными окружения (`PGPASSWORD`), а не в
  строке запуска: сообщение об ошибке его не содержит. Параметры Prisma из
  `DATABASE_URL` (`connection_limit`, `schema`…) libpq не понимает — адрес
  разбирается на части.
- Тайм-аут `pg_dump` — 10 минут.

## Образ

В runtime-образ бэкенда ставится `postgresql16-client` — той же major-версии,
что сервер (`postgres:16-alpine`): архив новее `pg_restore` 16 может не прочитать.

## Восстановление

```
cat trade-play-2026-10-19.dump.part* > trade-play-2026-10-19.dump   # если частей несколько
pg_restore --clean --if-exists --no-owner -d virex trade-play-2026-10-19.dump
```

## Что в дампе чувствительного

Почты, хэши паролей, зашифрованные ключи бирж (ключ шифрования
`CREDENTIALS_ENCRYPTION_KEY` в базе не лежит), id чатов Telegram. Чат с ботом —
облачный, не сквозное шифрование. Шифровать файл паролем не стали — владелец
не просил; это первое, что добавлять, если понадобится.

## Тесты

- Слот и «пора ли» (`backup-schedule.ts`): понедельник 00:00 UTC, догон
  пропущенного, повтор после перезапуска.
- Разбор `DATABASE_URL` в переменные libpq, имена частей.
- Сервис: не пора — ничего; пора — шлёт и пишет строку; Telegram не принял —
  строки нет, текст о сбое один раз за слот; чат не привязан — ничего.
