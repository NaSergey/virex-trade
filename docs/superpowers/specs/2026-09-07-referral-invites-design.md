# Инвайты: персональная реферальная ссылка

Дата: 2026-09-07

## Задача

У продукта нет способа отследить, кто кого привёл. Нужна персональная ссылка у
каждого пользователя: переход по ней и последующая регистрация закрепляют нового
пользователя за пригласившим, а пригласивший видит, сколько человек пришло по его
ссылке и сколько из них подключили ключ биржи — это второй и содержательный шаг
пути (см. «Готовность» в CLAUDE.md), а не просто факт регистрации.

Наград, инвайт-кодов, которые нужно создавать или включать явно, и сводного вида
для владельца в `/admin` в этой версии нет — YAGNI: ссылка одна и постоянная у
каждого, ничего не создаётся руками, а владелец видит функцию так же, как обычный
пользователь.

## Схема данных

Одно новое поле на `User`, без отдельной таблицы кодов:

```prisma
model User {
  ...
  invitedById  String?
  invitedBy    User?   @relation("Referrals", fields: [invitedById], references: [id], onDelete: SetNull)
  invitedUsers User[]  @relation("Referrals")
}
```

Ссылка пользователя — `<домен>/login?mode=register&ref=<его userId>`. `userId` уже
отдаётся фронту в `/auth/me`, отдельный «код» не нужен: `id` и так непрозрачный
UUID. Постоянство ссылки — прямое следствие того, что она строится из уже
существующего поля, а не из отдельной сущности с собственным жизненным циклом.

`onDelete: SetNull`: удаление аккаунта пригласившего не должно каскадом утаскивать
приглашённых — они просто теряют ссылку на источник, как и `Trade.userId` в
похожих местах схемы не предполагает каскадного удаления чужих данных.

## Бэкенд

**Регистрация.** `RegisterDto` получает необязательное поле `ref?: string`. В
`AuthService.register()` — если `ref` пришёл, ищем пользователя с таким `id`;
нашёлся — пишем в `invitedById` у создаваемого пользователя. Отсутствующий,
битый или чужой `ref` не валит регистрацию — это то же самое, что её отсутствие.
`id` в схеме объявлен как `String`, не `@db.Uuid`, поэтому `findUnique` с мусорной
строкой не бросает исключение, а просто не находит строку.

**Новый модуль `backend/src/referrals`**, по образцу `donations` — отдельная
функция продукта получает отдельный модуль, а не довесок к `auth`.

- `ReferralsService.getStats(userId): Promise<{ total: number; withKey: number }>`
  — два `prisma.user.count`: `{ invitedById: userId }` и то же с добавленным
  `exchangeConnections: { some: {} }`.
- **Ключ — это «подключён сейчас», а не «был подключён когда-то».** Отдельного
  флага «когда-либо подключал» нет: он бы разошёлся с реальным состоянием в
  момент отключения ключа (`settings.controller` такой путь уже поддерживает), и
  число обманывало бы пригласившего.
- `ReferralsController`: `GET /api/referrals/me` под `JwtAuthGuard`, отдаёт
  статистику текущего пользователя. Больше эндпоинтов не нужно — создавать или
  включать ссылку не из чего, отдавать чужую статистику некому.

## Фронтенд

- `AuthContext.register()` — необязательный параметр `ref`, кладётся в тело
  запроса `POST /auth/register`.
- `app/login/page.tsx` — читает `ref` из query-параметров страницы и прокидывает
  в `register()` при отправке формы. URL при переключении `mode` не меняется
  (`setMode` — локальный стейт, не `router.push`), поэтому `ref` в адресной
  строке переживает переключение между входом и регистрацией и перезагрузку
  страницы.
- `features/referrals/` — по образцу `features/donation`:
  - `api/hooks.ts`: `useReferralStats()` — `useQuery` на `GET /api/referrals/me`.
  - `ui/ReferralDialog.tsx` — одно окно без второго шага (в отличие от доната
    здесь нечего ждать в реальном времени): ссылка в readonly `Input` с кнопкой
    «Копировать» и строка вида «Приглашено: 5 · подключили ключ: 3».
- `widgets/top-nav/TopNav.tsx` — пункт в меню профиля рядом с донатом (та же
  пара `KeyValue` + кнопка), открывает `ReferralDialog` поверх текущей страницы.

## Тестирование

- `auth.service.spec.ts`: регистрация с валидным `ref` проставляет `invitedById`;
  с отсутствующим и с `ref`, которому не соответствует ни один пользователь, —
  не проставляет и не падает.
- `referrals.service.spec.ts`: `getStats` считает `total` и `withKey` верно,
  включая пользователя без приглашённых (`{ total: 0, withKey: 0 }`) и случай,
  когда приглашённый отключил ранее подключённый ключ (перестаёт входить в
  `withKey`, продолжает входить в `total`).

## Вне рамок этой версии

- Наград и любых форм геймификации за приглашения нет — при появлении такой
  задачи это отдельный дизайн: нужно решить вопрос злоупотреблений (сам себя
  пригласить со второго аккаунта и т. п.), которого без вознаграждения не
  существует.
- Сводного вида по рефералам в `/admin` нет — при необходимости добавляется
  отдельно, без изменений в схеме: данные для него уже есть в `invitedById`.
