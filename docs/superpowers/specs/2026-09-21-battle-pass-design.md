# Battle Pass: XP за игры, сезонные уровни и награды

Дата: 2026-09-21

## Задача

Игрок получает XP за игры раздела `/games`, копит уровень, забирает за уровни монеты. Сезон —
три месяца, по его окончании всё начинается с первого уровня. Отдельно — ежедневная награда за
заход, растущая с каждым днём подряд до седьмого. Прогресс живёт на новой странице профиля,
там же слот под героя, модели которого ещё рисуются.

Решения владельца, принятые в брейнсторме (2026-09-21):

- Сезон — **3 месяца**, в конце **сброс до первого уровня**; прошлые сезоны продукт не
  показывает.
- **Платного трека нет** — один бесплатный.
- Награда за уровень — **только монеты**; «бонусные баллы» из постановки это они и есть.
- Награды **забираются кнопкой**, а не падают сами.
- XP даёт **любая игра**: турнир, сессия бектеста/тренажёра, столы карточных игр (когда у них
  появятся правила), плюс активность в журнале сделок. Источники заводятся **реестром**, чтобы
  новая игра подключалась записью, а не правкой четырёх файлов.
- Прогресс показывает **новая страница `/profile`**.

## Сезон — календарный квартал, а не строка в таблице

`battlepass/season.ts`: `seasonKey(date) → '2026-Q4'`, `seasonBounds(key) → { startsAt, endsAt }`.
Чистые функции над UTC.

Таблицы сезонов нет намеренно. Сезон, который кто-то должен создать заранее, — это ещё одно
место, где забытая запись останавливает продукт: без строки следующего квартала XP перестал бы
начисляться молча. Квартал же известен из календаря, и «сезон начался» не событие, а смена
ключа, по которому пишется прогресс. Тот же приём, что у визитов в админке: выводится, а не
хранится.

Граница — UTC, как у `UserActivityMinute` и у всего остального в продукте. Второй часовой пояс
означал бы два ответа на вопрос «какой сегодня день».

Строки прошлых сезонов из базы не удаляются — джоб чистки ради этого заводить незачем, — но
**ни один эндпоинт их не отдаёт**: «прошлые сезоны не сохраняем» это решение о продукте, и
одной точки, где история не собирается, достаточно.

## Данные

```prisma
/// Прогресс Battle Pass за один сезон. Уровень не хранится — он функция от xp
/// (см. battlepass/levels.ts): правило начисления это соглашение, а не факт о
/// человеке, и сохранённый уровень пришлось бы пересчитывать задним числом при
/// любой его правке. Тот же довод, что у рейтинга турниров (tournaments/rating.ts).
model BattlePassProgress {
  userId       String
  user         User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  /// Ключ сезона: '2026-Q4'. Календарный квартал UTC, см. battlepass/season.ts.
  season       String
  xp           Int      @default(0)
  /// До какого уровня награды забраны. Забирают подряд и всё сразу: награда
  /// одного вида — монеты, и выбирать, какую монету получить раньше, незачем.
  claimedLevel Int      @default(0)
  updatedAt    DateTime @updatedAt

  @@id([userId, season])
  @@map("battle_pass_progress")
}

/// Журнал начисленного XP — по строке на событие. Нужен ровно за тем же, за чем
/// CoinTransaction: чтобы «откуда взялось» имело ответ и чтобы одно событие не
/// было оплачено дважды, сколько бы раз его ни разобрали.
model BattlePassXpEvent {
  id        String   @id @default(uuid())
  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  /// Сезон, в который начисление попало. Для выборки, не для ключа.
  season    String
  /// Ключ реестра: 'game.tournament', 'game.backtest', ...
  source    String
  /// Id того, за что начислено: турнира, сессии, сделки.
  refId     String
  /// Фактически начисленное — может быть 0, если упёрлись в дневной потолок.
  /// Строка нужна и в этом случае: она и есть отметка «событие разобрано».
  xp        Int
  createdAt DateTime @default(now())

  @@unique([userId, source, refId], map: "bp_xp_once")
  @@index([userId, season])
  @@index([userId, source, createdAt])
  @@map("battle_pass_xp_events")
}
```

Ключ `bp_xp_once` **не включает сезон**: турнир, доигранный в последнюю минуту квартала и
финализированный в первую минуту следующего, — одно событие, и оплачено оно должно быть один
раз. Сезон же берётся в момент начисления и остаётся в строке как признак выборки.

`User` получает обратные связи `battlePassProgress` и `battlePassXpEvents` — каскадом, как
остальное имущество аккаунта.

## Уровни и награды

`battlepass/levels.ts` — чистые функции, числа — константы `battlepass/battlepass.config.ts`:

- `MAX_LEVEL = 50`. Старт сезона — уровень 1; награды за него нет, её не за что давать.
- `xpToAdvance(fromLevel) = 100 + 20 * (fromLevel - 1)` — сколько XP нужно с уровня на
  следующий: 100 на первом, 1060 на сорок девятом, ≈28 400 за весь трек. При активной игре
  (около пятисот XP в день) трек проходится примерно за два месяца — то есть сезон в три
  месяца доигрывается с запасом, а не впритык.
- `levelFromXp(xp) → { level, xpIntoLevel, xpToNext }` — уровень выводится перебором по той же
  формуле; пятьдесят шагов дешевле любой попытки решить это в закрытом виде и не разойдётся с
  лестницей, которую рисует фронт.
- `rewardCoins(level) = 50 * (1 + floor((level - 1) / 10))` — 50 монет за уровни 2–10, 100 за
  11–20 и далее до 250; весь трек ≈7 400 монет за сезон. Это порядка пятнадцати долларов по
  курсу доната (`COINS_PER_USDT = 500`) за три месяца игры — заметно, но не обесценивает
  донат.

Числа — константы конфига, а не литералы по месту: кривую придётся править по живым данным, и
править её нужно в одном месте.

## Начисление XP: реестр источников

`battlepass/xp-registry.ts` — по образцу `notifications/registry.ts`: **единственный источник
правды о том, за что дают XP**. Сервис и API читают его; новая игра — запись, а не правка
четырёх файлов.

```ts
export type XpSource = 'game.tournament' | 'game.backtest' | 'game.table' | 'journal.tag';

export interface XpSourceDef {
  /** Заголовок для API и фронта (фронт переводит по ключу с откатом на него). */
  title: string;
  /** Начисляется ли сейчас. false — запись есть, кода начисления ещё нет. */
  enabled: boolean;
  /** База начисления за одно событие. */
  base: number;
  /** Надбавка за каждого обойдённого соперника. Есть только у турнира. */
  perOpponent?: number;
  /** Потолок XP из этого источника за сутки UTC. null — потолка нет. */
  dailyCap: number | null;
}
```

Числа живут в реестре, форма формулы — по месту вызова: контекст («сколько было участников»,
«какое место») знает только вызывающий, и тащить его в реестр значило бы описывать там каждую
будущую игру заранее.

Записи первой версии:

| Источник | Сколько | Потолок в сутки | Где вызывается |
|---|---|---|---|
| `game.tournament` | `100 + (участников − место) × 25` | 1000 | `TournamentsService.finalize`, в транзакции финала |
| `game.backtest` | 50 за завершённую сессию — только не турнирную: турнирные кончаются вместе с турниром и уже оплачены строкой выше | 300 | `BacktestService.finish`, в её транзакции |
| `game.table` | — | — | `enabled: false`: правил блэкджека и покера ещё нет |
| `journal.tag` | 15 за первую разметку сделки | нет | `TagsService.setTradeTags` |

Формула турнира повторяет рейтинг игры (`tournaments/rating.ts`): размер турнира входит в цену
победы, обыграть девятерых весомее, чем одного. Второй формулы того же смысла в продукте быть
не должно.

**Дневной потолок — не украшение, а единственная защита от фарма.** Турнир можно завести на два
своих аккаунта с нулевым взносом и коротким сроком, а сессию бектеста — создать и завершить за
секунды; без потолка уровень набивается за вечер и трек перестаёт что-либо значить. Потолок
считается суммой `BattlePassXpEvent.xp` за сегодня UTC по этому источнику; упёршееся начисление
пишет строку с `xp: 0` — событие разобрано, и повторно оно не придёт.

`journal.tag` потолка не требует: ключ `(userId, source, refId = tradeId)` даёт XP один раз на
сделку навсегда, сколько бы раз её ни переразмечали, а число сделок человек не печатает.

## `BattlePassService`

`backend/src/battlepass/`. Методы, меняющие данные, **принимают клиент транзакции**, как
`CoinsService`: XP начисляется только вместе с тем, ради чего его тронули. Отдельная транзакция
означала бы состояние, где турнир финализирован, а опыт за него не начислен.

- `award(tx, userId, source, refId, xp)` — записывает событие и двигает прогресс.
  Повторный вызов с тем же `(userId, source, refId)` упирается в `bp_xp_once` (P2002) и
  **проглатывается**, а не роняет транзакцию. Здесь это отличается от `CoinsService.credit`
  намеренно: там повтор означает попытку заплатить дважды и обязан всё откатить, здесь —
  что событие уже разобрано, и ронять из-за этого финал турнира с выплатами нельзя.
  Прогресс сезона создаётся `upsert` в момент первого начисления.
- `state(userId)` — сезон, xp, уровень, лестница, ежедневка. Без записи.
- `claim(userId)` — забрать всё доступное. Транзакция:
  1. читает прогресс, считает `level` из `xp`;
  2. `updateMany where { userId, season, claimedLevel: <прочитанное> } data { claimedLevel: level }`
     — compare-and-set в самом UPDATE, тот же приём, что у списания монет: двойной клик по
     «Забрать» иначе выдал бы награду дважды, и ни один из двух запросов не был бы неправ
     по отдельности. `count === 0` → откат;
  3. `coins.credit(tx, userId, rewardCoins(l), 'BATTLEPASS_REWARD', '<season>:<l>')` на каждый
     уровень из промежутка. Строка журнала на уровень, а не одна на клик: одно событие — одна
     строка, и уникальный ключ `coin_tx_once` тогда сторожит каждый уровень отдельно.
- `claimDaily(userId)` — ежедневная награда, см. ниже.

Новый вид `CoinTxKind`: `'BATTLEPASS_REWARD'` и `'DAILY_REWARD'` (`coins.service.ts` плюс
дублирующий doc-комментарий в `schema.prisma`).

## Ежедневная награда — без своей таблицы

Награда за заход: 50, 75, 100, 125, 150, 200, 300 монет за первый–седьмой день подряд (за полную
неделю ровно 1000 — столько же, сколько даёт новый аккаунт и один приглашённый). После седьмого
цикл повторяется с первого; пропущенный день возвращает к первому.

Состояние **не хранится отдельно**: награда — это строка `CoinTransaction` с
`kind = 'DAILY_REWARD'` и `refId = 'YYYY-MM-DD'` (UTC). Отсюда всё нужное:

- «сегодня уже забрал» — существование строки с сегодняшней датой, а гонку двух вкладок ловит
  существующий уникальный ключ `coin_tx_once (userId, kind, refId)`, а не проверка в коде;
- «какой день подряд» — семь последних строк этого вида: сколько подряд идущих дат назад от
  сегодняшней в них есть. Чистая функция `streakFrom(dates, today)` в `battlepass/daily.ts`.

Отдельная таблица со счётчиком стрика была бы вторым источником того же знания — и первым, что
разойдётся с журналом после ручной правки или отката.

Ежедневная награда **не даёт XP**: это награда за заход, а XP в продукте означает игру.

## API

`battlepass.controller.ts`, под общей аутентификацией:

- `GET /api/battlepass` → `{ season: { key, endsAt }, xp, level, xpIntoLevel, xpToNext,
  claimedLevel, pendingCoins, levels: [{ level, xp, coins, state: 'claimed' | 'ready' | 'locked' }],
  daily: { streak, day, claimedToday, coinsToday, nextCoins } }`
- `POST /api/battlepass/claim` → `{ claimedLevel, coins, balance }`
- `POST /api/battlepass/daily` → `{ streak, coins, balance }`

Лестницу отдаёт сервер, а не считает фронт: правило начисления одно, и второй его реализации в
браузере быть не должно — разойдутся при первой же правке кривой.

Фоновых сервисов модуль не добавляет: сезон вычисляется, сброс — смена ключа, награды забирает
сам человек. В разделении `api`/`worker` (`role.ts`) ничего не меняется.

## Фронтенд: страница `/profile`

`frontend/src/app/(app)/profile/page.tsx` → `views/profile/`. Пункт «Профиль» в выпадающем меню
шапки (рядом с «Настройками»), с точкой-индикатором, когда есть что забрать: награда, которую
никто не видит, не награда.

Блоки — `views/profile/components/`, не `widgets/`: страница одна, и правило продукта требует
подтверждённого грепом переиспользования на двух страницах.

- `HeroCard` — слот героя с заглушкой-силуэтом и бейджем уровня. Моделей ещё нет, и место под
  них занимается сейчас, чтобы страница не переезжала, когда они появятся. Выбора героя,
  косметики и инвентаря нет.
- `XpBar` — уровень, полоса до следующего, «столько-то XP до N».
- `DailyReward` — семь клеток с суммами, текущая подсвечена, кнопка «Забрать».
- `RewardTrack` — лестница уровней сезона: монеты за каждый, состояние клетки, одна кнопка
  «Забрать» на всё доступное, срок окончания сезона строкой.

Правила продукта, которые здесь легко нарушить:

- Страница **не игровая**: чёрное поле, скругления и палитра `--g-*` живут только внутри
  `/games` (см. CLAUDE.md). Профиль — про учётную запись, и строится общими средствами:
  `PageHead`, `SectionHead`, `KeyValue`, `Button`, нулевой радиус, цвета классами из
  `globals.css`.
- Слой страниц — `src/views/`, не `src/pages/`; проверять `npx next build`, а не только `tsc`.
- Тексты — `profile.*` в `ru.json` и `en.json`; названия источников XP фронт переводит по ключу
  с откатом на серверный `title` — тот же приём, что у реестра уведомлений.

Незабранные награды сгорают вместе с сезоном — прямое следствие решения «прошлые сезоны не
сохраняем». Поэтому срок окончания сезона стоит на странице рядом с кнопкой, а не в подсказке:
человек, потерявший монеты из-за незамеченной даты, прав.

## Сознательно не делаем

- **Премиум-трек** — решение владельца: один бесплатный.
- **Косметику, выбор героя, инвентарь** — награда только монеты; слот героя остаётся заглушкой
  до моделей.
- **«Возможности» за уровень** (скидка на взнос, повышенный потолок стола) — постановка их
  упоминает, но наградой выбраны монеты; функциональные бонусы меняют экономику турниров и
  требуют отдельного продуктового решения.
- **Историю прошлых сезонов** в интерфейсе.
- **Публичный показ уровня** (в лидерборде, в составе турнира) — не просили; уровень виден
  владельцу.
- **Начисление XP задним числом** за уже сыгранные турниры и размеченные сделки — счёт
  открывается с этого релиза.

## Известный риск

Турнир на два своих аккаунта даёт XP обоим, и потолок в 1000 XP в сутки его не запрещает, а
ограничивает: это примерно уровень в день на старте трека и заметно меньше ближе к пятидесятому.
Урон ограничен тем же, чем у реферального бонуса: монеты нельзя ни вывести, ни передать другому
игроку, предельный случай — раздутый игровой баланс на собственных аккаунтах. Требование взноса
больше нуля или минимального числа участников — отдельное продуктовое решение, а не тихая правка
сейчас.

## Тестирование

Чистые функции — юнит-тестами, они здесь и есть правила:

- `season.spec.ts` — границы кварталов, стык 31 декабря/1 января, UTC.
- `levels.spec.ts` — `levelFromXp` обратна `xpToAdvance` на всём треке, потолок `MAX_LEVEL`,
  суммы наград.
- `daily.spec.ts` — стрик: подряд, пропуск, седьмой день, восьмой (цикл заново), пустой журнал.
- `battlepass.service.spec.ts` — повторное `award` с тем же `refId` не начисляет второй раз и
  **не роняет** транзакцию; дневной потолок режет начисление и пишет строку с `xp: 0`;
  `claim` при гонке выдаёт награду один раз (второй CAS не проходит); `claim` без доступных
  уровней ничего не начисляет; `claimDaily` дважды за сутки — ошибка, а не вторая выплата.

В существующих спеках правится конструкторный список: `TournamentsService`, `BacktestService`
и `TagsService` получают `BattlePassService` (мок со спаем на `award`) — проверяемое поведение
этих тестов не меняется.
