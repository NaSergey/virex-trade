# Общая инфраструктура для игр между пользователями

Дата: 2026-09-20. Автор решений: владелец продукта, по итогам брейнсторма.

## Контекст и рамки

На витрине `/games` уже стоят карточки покера и блэкджека с меткой «Скоро» —
ассетов и игрового поля пока нет, фронтенд для них делается отдельно и позже.
Эта часть — только бэкенд, и только то общее, что понадобится **обеим** играм:
лобби столов, посадка/уход с эскроу фишек, канал реалтайма. Правила самой игры
(раздача, ставки, вскрытие рук) — вне рамок: сначала отдельный
спек+план на блэкджек, потом на покер, каждый берёт эту инфраструктуру как
готовый слой.

Формат обеих игр — **казино-логика ставок**, не турнирный: игрок садится за
стол на свою ставку (buy-in), играет раздачи одну за другой, может встать и
забрать остаток стека в любой момент. Это отдельная механика от
`TournamentsService` (фиксированный жизненный цикл лобби → старт → финиш с
призами) — переиспользуется только паттерн эскроу монет и структура
контроллера/DTO/ошибок.

Стол — постоянный (не пересоздаётся на каждую игру, как турнир), но не крутится
фоном 24/7: у него просто нет фонового цикла вообще, пока в нём нет игровой
логики (см. «Реалтайм» ниже) — существование стола между раздачами не стоит
процессу ничего, кроме строки в БД.

Столы создаёт пользователь сам — те же поля, что у турнира (ставки, лимит
мест, публичность/по ссылке), не фиксированный набор «касс».

## Модель данных

Плоские строковые статусы, как у `Tournament` (не Prisma-enum) — значения
расширяются без миграции схемы.

```prisma
model GameTable {
  id         String     @id @default(cuid())
  gameType   String     // "blackjack" | "poker"
  name       String
  visibility String     @default("private") // "public" | "private"
  status     String     @default("open")    // "open" | "closed"
  minBuyIn   Int
  maxBuyIn   Int
  maxSeats   Int
  creatorId  String?
  creator    User?      @relation(fields: [creatorId], references: [id], onDelete: SetNull)
  createdAt  DateTime   @default(now())
  closedAt   DateTime?
  seats      GameSeat[]
}

model GameSeat {
  id        String   @id @default(cuid())
  tableId   String
  table     GameTable @relation(fields: [tableId], references: [id], onDelete: Cascade)
  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  seatIndex Int
  stack     Int
  joinedAt  DateTime @default(now())

  @@unique([tableId, seatIndex])
  @@unique([tableId, userId])
}
```

**`GameSeat` — строка живёт, только пока игрок сидит; уход строку удаляет**, а
не помечает статусом. История не теряется — она уже лосслесно лежит в
`CoinTransaction` (см. ниже) — а живая строка на выбывшего означала бы, что
`@@unique([tableId, seatIndex])` навсегда занимает номер места и его больше
никому не отдать. Ровно тот же приём, что «визиты не хранятся, а выводятся» у
админки: не держать вторую копию того, что уже честно лежит в журнале.

`@@unique([tableId, userId])` не даёt занять два места за одним столом
одновременно и параллельно защищает от гонки: два одновременных запроса на
один `seatIndex` или от одного пользователя ловят `P2002`, а не порождают
две строки.

`CoinTxKind` (`backend/src/coins/coins.service.ts`) получает два новых
значения: `GAME_BUYIN`, `GAME_CASHOUT`.

## Эскроу фишек

Использует существующий `CoinsService.charge`/`credit` — ничего нового в самих
монетах, только новые `kind` и `refId = seat.id`.

- **Посадка (`join`)**: одна транзакция — выбрать свободный `seatIndex`
  (первый не занятый среди текущих `GameSeat` стола), создать строку места,
  затем `coins.charge(tx, userId, buyIn, 'GAME_BUYIN', seat.id)`. Не хватило
  монет — `charge` бросает `INSUFFICIENT_COINS`, транзакция откатывается
  целиком, места не остаётся. Гонка на один `seatIndex` — `P2002`, ловится и
  превращается в `GAME_SEAT_RACE` (клиент перечитывает стол и пробует другое
  место); это тот же принцип compare-and-set, что и у самого списания монет,
  только на уровне уникального индекса, а не отдельного столбца.
- **Уход (`leave`)**: транзакция — сначала удаление места, и стек берётся из
  возвращённой строки, а не читается отдельным запросом до него. `DELETE`
  берёт блокировку строки и отдаёт её актуальную версию; чтение до удаления
  оставляло бы окно, в котором игровая логика успевает изменить стек, и
  кэшаут уходил бы на устаревшую сумму — монеты исчезали бы из системы или
  печатались. Отсутствие строки (`P2025`) — это `GAME_NOT_SEATED`, а не 500:
  два одновременных ухода (двойной клик) иначе роняли бы второй запрос.
  Дальше `coins.credit(tx, userId, seat.stack, 'GAME_CASHOUT', seat.id)`.
- **Закрытие стола**: только создатель или владелец сервиса
  (`admin/owner.ts`, как `finishEarly` у турнира), и только когда стол пуст —
  силой закрыть стол с чужими деньгами на нём нельзя. Иначе
  `GAME_TABLE_NOT_EMPTY`.
- Довнос фишек посреди игры (rebuy) — не делаем: пока нет самой игры, не о чем
  довносить; если понадобится, это решение уровня блэкджека/покера, не общей
  инфраструктуры.

## REST API (`backend/src/games`)

Контроллер, сервис, DTO и ошибки — по образцу `tournaments/`.

- `POST /api/games/tables` — создать (`gameType`, `name`, `visibility?`,
  `minBuyIn`, `maxBuyIn`, `maxSeats`). Границы `maxSeats` по типу игры —
  константы в `games.config.ts` (блэкджек 1–7, покер 2–9), как
  `MIN_PLAYERS`/`MAX_PLAYERS` у турнира. **Создатель не садится за стол
  автоматически** — в отличие от турнира, где создатель всегда участник:
  здесь при создании ещё не выбрана сумма buy-in, и задавать стол для чужой
  игры, не садясь самому, — законный случай. Хочет играть — зовёт `/join`
  как любой другой.
- `GET /api/games/tables/mine` — где я сижу, **при любом статусе стола**, и
  где я только создатель — пока стол открыт. Место — это мои фишки, и его
  нельзя прятать из-за того, чем кончился стол: закрытый стол с живым местом
  в принципе возможен (см. «Открытая гонка» ниже), и тогда единственный путь
  к своим монетам — увидеть этот стол в списке.
- `GET /api/games/tables/public?gameType=` — открытые публичные столы без
  меня (`seats: { none: { userId } }`, как `listPublic` у турниров).
- `GET /api/games/tables/:id` — стол и список мест (`userId`, `seatIndex`,
  `stack`); карты/руки — предмет будущих спек, здесь их ещё нет. Доступен
  любому авторизованному пользователю по id, не только участникам — приватный
  стол защищён тем, что id никому не показан вне приглашения, а не проверкой
  членства (тот же принцип, что ссылка-приглашение турнира).
- `POST /api/games/tables/:id/join { buyIn }`
- `POST /api/games/tables/:id/leave`
- `DELETE /api/games/tables/:id` — закрыть (создатель/владелец, только пустой).

Ошибки — `backend/src/games/game-errors.ts`, тем же приёмом, что
`tournament-errors.ts` (фабрики `{message, code}`): `GAME_TABLE_NOT_FOUND`,
`GAME_TABLE_CLOSED`, `GAME_TABLE_FULL`, `GAME_ALREADY_SEATED`,
`GAME_NOT_SEATED`, `GAME_TABLE_NOT_EMPTY`, `GAME_BUY_IN_OUT_OF_RANGE`,
`GAME_SEAT_RACE`, `GAME_NOT_CREATOR_OR_ADMIN` — плюс существующий
`INSUFFICIENT_COINS` из `coins`.

## Реалтайм: WebSocket

Первый WS-канал в проекте (турниры сейчас живут на поллинге раз в 5с через
React Query — для покера с быстрыми ходами это заметная задержка и двойная
нагрузка на опрос одного и того же состояния).

- `GamesGateway`, `@WebSocketGateway({ path: '/api/games/socket.io',
  namespace: '/games' })`.
- **Путь хендшейка задаётся явно и обязан лежать под `/api/`.** `namespace`
  — это не HTTP-путь: рукопожатие socket.io идёт своим адресом, по умолчанию
  `/socket.io/`. Наружу проксируются только `/api/*` и `/auth/*`
  (`deploy/Caddyfile`, `next.config.ts`), всё прочее забирает Next, а гейт
  `proxy.ts` уводит неизвестный путь на `/login` — канал по умолчанию не
  доезжал бы до бэкенда ни в проде, ни локально. Клиент обязан указывать
  тот же `path`.
- Аутентификация в handshake: клиент передаёт access-токен в
  `socket.handshake.auth.token`; гейтвей проверяет его тем же секретом, что
  `JwtStrategy` (`auth/jwt-secret.ts`) — в вебсокете нет Bearer-заголовка,
  поэтому токен идёт явным полем, а не переиспользует HTTP-guard.
- **Отказ выдаётся из middleware (`server.use` в `afterInit`), а не из
  `handleConnection`.** socket.io шлёт пакет CONNECT до `handleConnection`,
  поэтому разрыв после него клиент видит не как отказ, а как обрыв связи — и
  переподключается тем же мёртвым токеном бесконечно (а живёт он 15 минут,
  то есть любая долго открытая страница стола гарантированно это словит).
  Отказ из middleware приходит как `connect_error`, и автопереподключение не
  запускается. Проверки `userId` в самих обработчиках при этом остаются:
  граница аутентификации у канала с деньгами должна падать закрыто, если
  middleware когда-нибудь тронут.
- Комната socket.io = `tableId`. Событие `join_table` от клиента — это только
  подписка сокета на обновления конкретного стола, не посадка за него:
  посадка остаётся REST-вызовом `/join`, чтобы деньги двигались только через
  транзакцию с эскроу, а не через сообщение сокета.
- После любой мутации стола (`join`/`leave`/`close`) сервис зовёт
  `gateway.broadcastTableState(tableId)` — рассылает комнате снимок текущих
  мест. Клиенты стола не поллят вообще.
- **Отдельного реестра «движков» или таймеров пока не заводим.** Без игровой
  логики (раздач, ходов) нечему тикать — комнаты socket.io сами по себе и
  есть весь нужный «живой» стол: сокет существует, только пока к столу кто-то
  подключён. Требование «не работать 24/7» тем самым выполняется отсутствием
  фонового цикла, а не механизмом управления его жизнью. Первый таймер
  (например, время на решение в раздаче) появится вместе с игровой логикой в
  спеке блэкджека — и тогда встанет вопрос, где он живёт.
- Гейтинг по роли (`role.ts`) не нужен: `GamesModule` регистрируется
  безусловно, как остальные фичевые модули. В `worker` HTTP-порт не
  открывается (`app.listen()` не вызывается), поэтому сокеты там физически
  недостижимы — тот же принцип, что и у обычных контроллеров, которые тоже
  регистрируются без гейта по роли.

## Тестирование

Unit-тесты `games.service.spec.ts` по образцу `tournaments.service.spec.ts`
(мокнутый Prisma и `CoinsService`):

- `join` в полный стол → `GAME_TABLE_FULL`.
- `join` с недостаточным балансом → `INSUFFICIENT_COINS`, место не создаётся.
- `join` за уже занятое место (гонка) → `GAME_SEAT_RACE`, не 500.
- `leave` корректно начисляет стек и освобождает `seatIndex` для следующего.
- `close` непустого стола → `GAME_TABLE_NOT_EMPTY`.
- `close` чужого стола не создателем и не владельцем → `GAME_NOT_CREATOR_OR_ADMIN`.

## Открытая гонка: `close` против незакоммиченного `join`

Проверка пустоты живёт в самом `updateMany` (`seats: { none: {} }`), и от
гонки «прочитал пусто — записал» это защищает. Но на READ COMMITTED
подзапрос не видит INSERT из ещё не закоммиченной транзакции `join`, а `join`
в строку стола ничего не пишет — конфликта записей между ними нет, и обе
транзакции коммитятся. Результат: стол `closed`, а за ним место с деньгами.

Деньги при этом не теряются: `leave` статус стола не проверяет намеренно, и
стол виден в «моих» при любом статусе (см. выше) — то есть выйти и забрать
стек можно всегда. Полное закрытие гонки требует либо `SELECT … FOR UPDATE`
на строке стола в `join`, либо serializable-транзакции в `close`, а обе
противоречат конвенции кодовой базы («уникальные индексы и compare-and-set,
не блокировки»). Холостой `updateMany` по столу внутри `join` не помогает:
EvalPlanQual перечитывает саму строку, но подзапрос `NOT EXISTS` может
остаться на прежнем снимке. **Решение отложено до владельца** — цена вопроса
сейчас нулевая, потому что игровой логики ещё нет и стол закрывает только
его создатель.

## Вне рамок

- Правила и состояние самой раздачи (карты, ставки, side-pot, hit/stand,
  таймер хода) — блэкджек следующим спеком, покер после.
- Довнос фишек (rebuy), обработка обрыва соединения посреди раздачи
  (auto-fold/auto-stand) — вместе с игровой логикой каждой игры. Когда дойдёт
  до rebuy, помнить: `refId` строки журнала равен `GameSeat.id`, и второй
  `GAME_BUYIN` на то же место упрётся в `coin_tx_once`. Соседний модуль эту
  же задачу уже решил дискриминатором в ключе — `feeRef` в
  `tournaments.service.ts`.
- Фронтенд и ассеты — по договорённости, не сейчас. Клиент обязан
  подключаться с тем же `path: '/api/games/socket.io'`.
- **Персональный канал игрока.** Сейчас рассылка только веерная: снимок
  уходит в комнату стола целиком. Блэкджеку этого хватает, покеру — нет:
  карманные карты нельзя слать всем. Это одна строка в middleware
  (`client.join('user:' + payload.sub)`) плюс адресный emit, но заводить её
  до того, как появился первый получатель, незачем — встанет вместе с
  покерной раздачей.
- **Цена и срок жизни стола.** Создание стола ничего не стоит,
  `ThrottlerGuard` на контроллере не стоит, сам из `open` стол не выходит, а
  `listPublic` отдаёт 50 новейших — один аккаунт может закопать публичное
  лобби. У турниров форма та же, но их лобби опустошается стартом. Решать,
  когда лобби станет видно живым людям.
