# Хранилище свечей BTC: один источник графика на шести таймфреймах

Дата: 2026-09-10

## Задача

Терминалу бектеста нужен полный график биткоина — от минутного до дневного, с 2018
года, — чтобы выдавать пользователю случайный исторический отрезок и давать на нём
проверять свою стратегию. График должен лежать в базе и сам догоняться, а не тянуться
из внешнего API на каждый показ.

Это первая из двух работ. Вторая — сам терминал (случайный отрезок, симуляция сделок,
интерфейс, режим живой торговли) — проектируется отдельно, когда данные уже есть.
Здесь только источник и хранилище.

## Что есть сегодня и почему этого мало

`market-events` держит две таблицы свечей BTCUSDT, обе с Bybit
(`category=linear`, то есть перпетуум):

- `daily_prices` — дневные свечи с 2019-01-01, поля `open`/`close`/`changePct`;
- `hourly_prices` — часовые с 2024-01-01, с добавленными `high`/`low`.

Обе кормят аналитику по дням недели и часам (`MarketEventsService`), и через неё —
сигнал `mkt.hour` в уведомлениях. Для бектеста они не годятся по трём причинам сразу:
нет минутных, пятиминутных, пятнадцатиминутных и четырёхчасовых свечей; глубины
2018 года нет ни у одной; **и главное — у Bybit её и не может быть**, потому что
BTCUSDT-перпетуум там торгуется только с 2020 года.

Проверено живым запросом: Binance spot отдаёт BTCUSDT с **2017-08-17**, то есть 2018
закрыт полностью и с запасом.

## Решение в одну строку

Одна таблица `price_candles`, один сервис синхронизации, один источник (Binance spot),
шесть таймфреймов. Старые `daily_prices` / `hourly_prices` и оба их сервиса синка
удаляются, `market-events` становится потребителем нового модуля.

Требование владельца, из которого выведено всё остальное: **не заводить вторую копию
данных биткоина — за них отвечает ровно один блок бэкенда.**

## Объём

Начало истории — **2018-01-01**, одной константой. У Binance данные есть с 2017-08-17,
то есть требование «с 2018 года» закрывается с запасом.

С 2018-01-01 по сегодня:

| ТФ | строк | запросов по 1000 |
|---|---|---|
| 1m | ~4.57 млн | 4572 |
| 5m | ~914 тыс | 915 |
| 15m | ~305 тыс | 305 |
| 1h | ~76 тыс | 77 |
| 4h | ~19 тыс | 20 |
| 1d | ~3.2 тыс | 4 |
| **всего** | **~5.9 млн** | **~5900** |

На диске — порядка 750–800 МБ вместе с индексом.

Оговорка на будущее: цикл ходит **только вперёд** от `MAX(time)`, поэтому если однажды
захочется добрать 2017-й, уменьшения константы не хватит — понадобится разовый проход от
новой даты до самой ранней сохранённой свечи. Это отдельная маленькая работа, а не
бесплатное следствие. Закладываться на неё сейчас незачем, но знать об этом свойстве
надо, чтобы не пообещать лишнего.

## Схема

```prisma
model PriceCandle {
  symbol    String   // 'BTCUSDT'
  timeframe Int      // длительность свечи в МИНУТАХ: 1, 5, 15, 60, 240, 1440
  time      DateTime // время ОТКРЫТИЯ свечи, UTC
  open      Float
  high      Float
  low       Float
  close     Float
  volume    Float

  @@id([symbol, timeframe, time])
  @@map("price_candles")
}
```

### Почему нет `id String @default(uuid())`

Во всех остальных моделях проекта он есть — здесь его быть не должно. На 5.9 млн строк
это ~220 МБ данных плюс собственный индекс ~265 МБ ради колонки, к которой не обратится
никто: свечу адресуют символом, таймфреймом и временем, а не суррогатным ключом. Причём
уникальный индекс по `(symbol, timeframe, time)` всё равно понадобился бы рядом —
иначе дубли ничем не закрыты.

Составной первичный ключ `(symbol, timeframe, time)` — ровно тот индекс, которым
читается диапазон свечей (`WHERE symbol=? AND timeframe=? AND time BETWEEN ? AND ?`),
и он же физически запрещает дубли. Один индекс на таблицу вместо двух, ~750 МБ вместо
~1.25 ГБ.

### Почему `timeframe` — минуты числом, а не строка

`'15m'` у Binance, `'15'` у Bybit, `'M15'` у следующего источника: строка расползётся
ровно так же, как расползся бы таймфрейм сделки, будь он тегом, — и по той же причине
в CLAUDE.md он сделан полем с фиксированным списком.

Число — это ещё и арифметика. Правило «свеча закрыта, если `time + timeframe*60000 + 30000 <=
now`» одно на все шесть таймфреймов, а не шесть частных случаев. Запас в 30 секунд страхует от
дрейфа часов сервера вперёд относительно биржи: без запаса ушедшие вперёд часы дали бы запись
ещё формирующейся свечи, а `skipDuplicates` и курсор по максимуму времени означают, что такая
строка уже никогда не исправится.

### Почему нет `changePct`

Он есть в обеих старых таблицах, но выводится из `open` и `close` одним вычитанием.
Хранить его — 50 МБ ради экономии одной операции на чтении. `MarketEventsService`
считает его на месте.

### Почему `symbol` остался, хотя значение одно

Добавить ETH позже — это вставка строк. Вернуть выкинутую колонку в таблицу на 5.9 млн
строк — это её перезапись. Цена присутствия колонки несопоставимо ниже цены её
отсутствия.

## Синхронизация: один цикл, режима «бэкфилл» не существует

Главное решение спеки. **Отдельного кода первоначальной заливки нет.** Есть один цикл,
который для каждого таймфрейма делает одно и то же:

```
курсор = MAX(time) по (symbol, timeframe)   ← или START (2018-01-01), если пусто
пока курсор < сейчас:
    страница = Binance klines(symbol, tf, startTime = курсор+1, limit = 1000)
    если страница пуста -> выход
    закрытые = свечи страницы, где time + tf*60000 + 30000 <= now
    если закрытых нет -> выход            ← догнали хвост, дальше только текущая свеча
    createMany(закрытые, skipDuplicates)
    курсор = time последней ЗАКРЫТОЙ свечи страницы
    пауза 300 мс
```

Курсор двигается по **полученной** закрытой свече, а не по «успешно вставленной»:
`skipDuplicates` может вернуть ноль записей на странице, которая уже лежит в базе, и
курсор, привязанный к числу вставок, застрял бы на месте навсегда.

На пустой базе он идёт от 2018 и упирается в «сегодня» примерно через 30 минут. На
заполненной делает один запрос, получает полтора десятка новых минуток и выходит. Это
один и тот же код, разница только в числе итераций.

Отсюда три свойства, ради которых так и сделано:

- **Курсор не хранится нигде** — он выводится из самих данных. Нечему рассинхронизироваться
  с таблицей, нечего чинить руками, нет состояния, которое переживёт правку данных и
  начнёт врать.
- **Прерывание безопасно в любой момент.** Контейнер упал на 40% истории — следующий
  старт продолжит с той же свечи. Никакого «продолжить или начать заново».
- **Пробел в истории невозможен**, потому что запись всегда идёт строго вперёд от
  максимума. Именно это делает `MAX(time)` законным курсором, а не догадкой. Если бы
  заливка шла назад от «сегодня», а дозаливка вперёд, понадобились бы два курсора и
  учёт дыр между ними.

Настоящий пропуск в истории самой биржи (простой Binance) цикл проходит сам: запрос от
`курсор+1` вернёт следующие существующие свечи, курсор перепрыгнет пробел.

### Ловушка: Binance листается вперёд, Bybit — назад

В `BybitMarketService.getKlinesRange` лежит комментарий, что пагинация обязана идти
**назад**: Bybit на диапазон отдаёт самые новые свечи, поэтому там двигают `end`.
Binance ведёт себя противоположно — отдаёт `limit` свечей начиная от `startTime`, по
возрастанию. Код, скопированный из соседнего файла по аналогии, будет работать
неправильно и молча: страницы поедут не в ту сторону. Поэтому клиент Binance пишется с
нуля, а не правкой копии бибитовского клиента.

Оборотная сторона того же свойства: на догнанной базе каждый тик тратит по одному
запросу на таймфрейм впустую — приходит только текущая незакрытая свеча, она
отфильтровывается, цикл выходит. Шесть лишних запросов раз в 15 минут; платить за это
отдельным состоянием «мы уже в хвосте» дороже, чем сами запросы.

### Порядок обхода — от крупного к мелкому

1d → 4h → 1h → 15m → 5m → 1m.

Дневной график с 2018 года доступен через минуту после первого старта, минутка доезжает
последней. В обратном порядке все шесть таймфреймов оставались бы пустыми 25 минут
подряд.

### Частота и лимиты

Запуск на `OnApplicationBootstrap` плюс `setInterval` раз в 15 минут — тот же паттерн,
что у нынешних `DailyPriceSyncService` / `HourlyPriceSyncService` (там 30 минут). Флаг
`syncing` не даёт таймеру начать второй проход поверх ещё идущего первого.

Пауза 300 мс между запросами — это ~3.3 запроса в секунду. Вес запроса klines с
`limit=1000` у Binance равен 5, то есть ~1000 единиц веса в минуту при лимите 1200.
Запас есть, но он невелик, поэтому клиент **обязан понимать 429 и отступать**, а не
терять страницу молча.

Свежесть в 15 минут выбрана осознанно: бектест идёт по случайным историческим отрезкам,
где сегодняшняя минутка не участвует вовсе. Живая цена для режима реальной торговли —
это стрим, её незачем класть в базу, и проектируется она вместе с терминалом.

## Границы модуля

```
backend/src/market-data/          ← единственный владелец price_candles
  binance-klines.client.ts        единственная точка выхода наружу
  timeframes.ts                   шесть разрешённых ТФ + арифметика закрытия
  price-sync.service.ts           цикл выше
  market-data.service.ts          getCandles / getCoverage
  market-data.controller.ts       /api/market-data/*
  market-data.module.ts           exports: MarketDataService

market-events/                    ← потребитель, аналитика по дням недели и часам
backtest/ (позже)                 ← ещё один потребитель того же сервиса
```

Публичный контракт — два метода:

```ts
getCandles({ symbol?, timeframe, from?, to?, limit? }): Promise<Candle[]>  // oldest-first
getCoverage(symbol?): Promise<Array<{ timeframe, from, to }>>
```

- **`prisma.priceCandle` не трогает никто, кроме `MarketDataService`.** Это и есть «один
  блок, отвечающий за данные биткоина»: у таблицы один читатель-владелец, у всех
  остальных — вызов сервиса.
- **`getCoverage` нужен терминалу сразу, а не «на будущее».** Чтобы выдать случайный
  отрезок, надо знать, между какими датами можно бросать кубик, — и знать отдельно по
  каждому таймфрейму: пока идёт первый бэкфилл, у 1d история с 2018, а у 1m ещё только
  до середины пути.
- **Таймфрейм вне списка из шести — 400, а не пустой ответ.** Пустой массив на `tf=30`
  неотличим от «данные ещё не докачались», и разбираться в этом будут долго.
- **Клиент Binance живёт здесь, а не в `exchanges/adapters/`.** Там адаптеры счёта
  пользователя — с ключами, сделками, позициями, правилом read-only из CLAUDE.md. Публичный
  источник цены рядом с ними заявлял бы седьмую биржевую интеграцию, которой нет: ключей
  он не просит и к аккаунтам отношения не имеет.

Эндпоинты `GET /api/market-data/candles` и `GET /api/market-data/coverage` — оба под
`JwtAuthGuard`, как соседний `market-events.controller`. Данные публичные, но открытый
эндпоинт сделал бы из сервера бесплатный прокси к истории BTC для кого угодно.

Ответ отдаётся объектами, а не массивами в стиле самой биржи: экономия на именах полей
съедается gzip'ом почти целиком, а читаемость контракта стоит дороже.

`limit` ограничен сверху 5000 свечами.

## Перевод market-events

Читателей старых таблиц ровно четверо:

| Файл | Было | Стало |
|---|---|---|
| `market-events.service.ts:34` | `prisma.dailyPrice` | `marketData.getCandles({ timeframe: 1440 })` |
| `market-events.service.ts:65,103` | `prisma.hourlyPrice` | `marketData.getCandles({ timeframe: 60 })` |
| `scripts/volatile-hour-preview.ts:35` | `prisma.hourlyPrice` | `price_candles`, `timeframe: 60` |
| `daily-price-sync.service.ts`, `hourly-price-sync.service.ts` | — | удаляются целиком |

`changePct` больше не колонка — три метода `MarketEventsService` считают его на месте.

Не затронуты, вопреки ожиданию:

- **`AnalyticsService.getVolatility`** — ходит на Bybit живым запросом
  (`analytics.service.ts:256`), а не в наши таблицы.
- **`BybitMarketService`** — остаётся жить целиком: его `getKlines`/`getKlinesRange`
  держат `trades/trade-context.service.ts` и `indicators.service.ts` по произвольным
  символам пользователя. Мы отбираем у него только двух вызывающих из `market-events`.

Миграция Prisma создаёт `price_candles` и удаляет `daily_prices` с `hourly_prices`.
Данные в них не жаль: они полностью воспроизводятся из Binance первым же проходом.

### Риск, который нельзя пропустить: пороги mkt.hour

Вместе с таблицей меняется источник — Bybit linear-перпетуум на Binance spot. Этими же
числами кормится сигнал `mkt.hour` (`market-alerts.service.ts:291-292` вызывает
`getWeekdayHourStats` и `getCorrelation`), а его пороги, по CLAUDE.md, **подбирались
глазами по живой таблице** через `volatile-hour-preview.ts` — и там же записано, что шум
на клетке порядка десяти процентов.

Спот и перпетуум ходят почти вплотную, так что сдвиг, скорее всего, утонет в этом шуме.
«Скорее всего» проверкой не является. Поэтому отдельным шагом плана: **после того как
докачается `timeframe: 60`, прогнать `volatile-hour-preview.ts` и сравнить с тем, что
сигнал говорит сегодня.** Если пресеты поедут заметно — их правка решение владельца, а
не то, что подкручивается по дороге.

## Чем проверяем

Юнит-тесты (паттерн `*.spec.ts`, моки prisma и клиента) на то, что ломается тихо:

- **Граница закрытой свечи.** 4h-свеча, открытая в 12:00, не попадает в базу в 15:59 и
  обязана попасть в 16:00. Это место, где `c.time < todayStart` из старого кода
  обобщается на шесть таймфреймов; ошибка здесь даёт вечно недорисованную последнюю
  свечу на графике.
- **Возобновление курсора.** База, оборванная на середине истории, продолжается с той же
  свечи — не с начала и не с «сейчас».
- **429 от Binance** приводит к отступлению и повтору, а не к молча потерянной странице.
- **Валидация таймфрейма** отвечает 400, а не пустотой.

Двумя тестами не заменяется:

- **Свободное место на VPS до запуска.** ~800 МБ таблица плюс WAL на вставке 6 млн
  строк. Узнать, что места нет, надо до бэкфилла, а не на 70% его.
- **Сверка `market-events` до и после** на одном периоде: форма чисел обязана совпасть, а
  расхождение — объясняться только разницей источников.

Изменение крупное (новая модель, миграция, новый модуль), поэтому билд и typecheck
гоняются без отдельного вопроса — по правилу из глобального CLAUDE.md.

## Что осознанно не делается

- **Живая цена по вебсокету.** Режим реальной торговли в терминале её потребует, но
  стриму не место в хранилище истории: он ничего не хранит. Решение — проксировать WS
  через бэкенд или подключаться к Binance напрямую с фронта — принимается вместе с
  дизайном терминала.
- **Агрегация старших таймфреймов из минуток на лету.** Она убрала бы 1.3 млн строк из
  5.9, но каждый показ 4h-графика на 500 свечей означал бы свёртку 120 тысяч минутных
  строк. Binance отдаёт каждый таймфрейм готовым — платить процессором за то, что даётся
  бесплатно, незачем.
- **Дампы с data.binance.vision.** Свели бы первый бэкфилл минуток с получаса до минут,
  но ценой второго кодового пути, распаковки ZIP, разбора CSV и второго внешнего
  контракта, который ломается отдельно от API. Полчаса разово на базу того не стоят.
- **Отдельная таблица состояния синка.** Курсор выводится из данных; таблица состояния
  была бы вторым источником правды о том же самом.
