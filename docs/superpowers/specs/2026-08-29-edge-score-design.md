# Edge Score — единая оценка качества системы

## Проблема

Разбор конкурентов ([[virex_competitor_landscape]], закреплено разговором в этой сессии)
показал: у Edgewonk есть собственный «Edge Score» — одна composite-оценка вместо десятка
разрозненных чисел. У Virex в `SummaryStrip`
([frontend/src/views/overview/components/SummaryStrip.tsx](../../../frontend/src/views/overview/components/SummaryStrip.tsx))
уже есть Winrate и Profit Factor каждый сам по себе, но нет одного числа, отвечающего на
вопрос «система вообще рабочая?».

Изобретать свою формулу с нуля означало бы либо взвешенный композит на глазок (не
объяснить, откуда веса), либо ещё один непрозрачный «AI score» вроде Thrive — оба
варианта расходятся с тем, как в проекте уже устроена вся остальная аналитика:
`HabitsService` использует пермутационный тест и поправку Бенджамини–Хохберга именно
чтобы не выдавать шум за находку. Edge Score должен быть той же породы — цитируемая,
проверяемая формула, а не сочинённая под красивую цифру.

## Решение

### Формула — System Quality Number (Van Tharp)

Признанная метрика качества торговой системы:

```
SQN = √N × mean(closedPnl) / stdev(closedPnl)
```

Классическая версия нормирует на R-мультипликатор (результат относительно риска на
сделку), но это требует стоп-лосса на каждой сделке, а он у Virex необязателен
(`Trade.stopLoss` — `Float?`, комментарий в схеме прямо говорит «у тех, кто держит стоп в
голове» он всегда `null`). У SQN есть официально равноценный вариант прямо на P&L без
R-нормировки — им и считаем. Он грубее (не различает сделку на 100 USDT и на 10 000 USDT
риска), но не требует данных, которых у половины сделок нет.

Считается внутри уже существующего `TradesService.stats()`
([backend/src/trades/trades.service.ts:742-804](../../../backend/src/trades/trades.service.ts)) —
на том же массиве `trades` (схлопнутые позиции), что уже строит `equity`. Новый эндпоинт
не нужен.

```ts
const MIN_SQN_POSITIONS = 30; // порог значимости самой SQN (Van Tharp), не число Virex

// ...внутри stats(), после того как totalTrades и totalPnl уже посчитаны...
let sqn: number | null = null;
if (totalTrades >= MIN_SQN_POSITIONS) {
  const mean = totalPnl / totalTrades;
  const variance =
    trades.reduce((a, t) => a + (t.closedPnl - mean) ** 2, 0) / (totalTrades - 1);
  const stdev = Math.sqrt(variance);
  sqn = stdev > 0 ? Number(((Math.sqrt(totalTrades) * mean) / stdev).toFixed(2)) : null;
}
```

`TradeStats` ([backend/src/trades/trades.service.ts:6-19](../../../backend/src/trades/trades.service.ts))
получает поле `sqn: number | null` — `null` и при N<30, и в вырожденном случае
`stdev === 0` (все сделки с одинаковым P&L). Дублируется в
[frontend/src/entities/trade/api/types.ts:105-118](../../../frontend/src/entities/trade/api/types.ts)
(`TradeStats`), по тому же принципу, что и остальные типы ответов — без общего пакета
типов бэкенд/фронт, копия синхронизируется вручную, как везде в проекте.

### Перевод в 0–100 — на фронте, чистой функцией

Новый файл `frontend/src/shared/lib/utils/edgeScore.ts` — не в `views/overview`, потому
что это не специфика Обзора, а универсальный пересчёт числа (как `format.ts` рядом).

Опорные точки — широко цитируемая шкала Тарпа (несколько независимых источников
воспроизводят её с небольшими расхождениями в границе «средняя/хорошая»; здесь взята
чаще встречающаяся версия, это не дословная цитата из его книги — прямого доступа к
первоисточнику нет):

| SQN | 0 | 1.6 | 2.0 | 2.5 | 3.0 | 5.0 | 7.0 |
|---|---|---|---|---|---|---|---|
| Score | 0 | 25 | 40 | 55 | 70 | 88 | 100 |
| Ярлык | — | плохая | ниже среднего | средняя | хорошая | отличная | превосходная / грааль |

```ts
const POINTS: Array<[sqn: number, score: number]> = [
  [0, 0],
  [1.6, 25],
  [2.0, 40],
  [2.5, 55],
  [3.0, 70],
  [5.0, 88],
  [7.0, 100],
];

/** SQN → 0..100 кусочно-линейной интерполяцией по шкале Тарпа. Клампится по краям. */
export function sqnToScore(sqn: number): number {
  if (sqn <= 0) return 0;
  if (sqn >= 7) return 100;
  for (let i = 1; i < POINTS.length; i++) {
    const [x1, y1] = POINTS[i - 1];
    const [x2, y2] = POINTS[i];
    if (sqn <= x2) return Math.round(y1 + ((sqn - x1) / (x2 - x1)) * (y2 - y1));
  }
  return 100; // недостижимо при упорядоченных POINTS — успокаивает TS
}

export type SqnTier = 'poor' | 'belowAverage' | 'average' | 'good' | 'excellent' | 'superb' | 'holyGrail';

/** Ярлык уровня по границам той же шкалы — для тултипа, не для основной цифры. */
export function sqnTier(sqn: number): SqnTier {
  if (sqn < 1.6) return 'poor';
  if (sqn < 2.0) return 'belowAverage';
  if (sqn < 2.5) return 'average';
  if (sqn < 3.0) return 'good';
  if (sqn < 5.0) return 'excellent';
  if (sqn < 7.0) return 'superb';
  return 'holyGrail';
}
```

`sqnTier` — только в `title=` подсказку на ячейке (см. ниже), не как отдельный видимый
текст: в `SummaryStrip` ни у Winrate, ни у Profit Factor нет текстовой качественной
подписи, только число и `GaugeBar` — новая ячейка обязана читаться тем же языком, а не
вставлять «Хорошая система» посреди строки чисел.

### Место — десятая ячейка в `SummaryStrip`, не отдельный блок

`SummaryStrip` уже строит `metrics: Metric[]` и рендерит по одному `.mcell` на элемент
([frontend/src/views/overview/components/SummaryStrip.tsx:44-70](../../../frontend/src/views/overview/components/SummaryStrip.tsx)),
с `GaugeBar` у Winrate/Profit Factor. CSS-сетка держится на `nth-child(An+B)`
(`.mcell:nth-child(3n+1)`, `:nth-child(2n)` и т.п.) — это модульная раскладка «сколько
колонок в ряд», а не жёстко «ровно 9 ячеек», так что десятая ячейка встаёт без правок CSS.

Добавляется вторым элементом массива `metrics`, сразу после Net P&L/до счётчика сделок —
это заголовочная метрика качества, ей место рядом с итоговым результатом, а не в хвосте
рядом с Fees/Best/Worst:

```ts
{
  label: 'Edge Score',
  value: stats.sqn == null ? '—' : String(sqnToScore(stats.sqn)),
  gauge: stats.sqn == null ? undefined : { fill: sqnToScore(stats.sqn), threshold: 40 },
},
```

(`threshold: 40` — граница «средней» системы по той же шкале, риска `GaugeBar` красит
заливку в тревожный цвет ниже неё, ровно как у Winrate с порогом 50.)

`title` на `.mcell` с `sqnTier`-ярлыком добавляется, только если `stats.sqn != null` —
у отсутствующего числа нет уровня, который стоило бы подписывать.

### Период — тот же `effectiveDays`, что у всего Обзора

`stats.sqn` считается за период, выбранный в `PeriodStrip`, а не всегда «за всё время»:
короткий период чаще упрётся в N<30 и покажет «—» — это ожидаемо и честно, не отдельный
случай для обработки.

## Что не меняется

- Контракт `/api/trades/stats` — только новое поле `sqn`, остальные не трогаются.
- `equity`, вся остальная логика `stats()` — без изменений.
- CSS-сетка `SummaryStrip` — без изменений (см. выше про `nth-child`).
- `HabitsService`/«Цена привычек» — отдельная, уже готовая метрика; Edge Score с ней не
  смешивается ни в одной формуле (см. «Проблема» — раздельные числа отвечают на разные
  вопросы, слияние в одну цифру закрыло бы оба).

## Риски / на что смотреть при реализации

- **Границы шкалы — не дословная цитата.** Несколько независимых источников по-разному
  проводят стык «средняя/хорошая» (2.0–2.5 против 2.5–2.9) — если пользователь явно
  сверится с другим сайтом и увидит другие цифры, это не баг реализации, а факт, что у
  народной метрики нет единого канонического текста без покупки книги Тарпа.
- **PnL-версия грубее R-версии.** Не различает риск разного масштаба между сделками —
  однострочная оговорка в тултипе (`sqnTier`) уместна, отдельного UI-предупреждения не
  заводим — это увеличило бы блок ради оговорки, которая интересна не всем.
- **Вырожденный `stdev === 0`.** Все сделки периода с одинаковым `closedPnl` (крайне
  маловероятно при N≥30, но не невозможно на синтетических/тестовых данных) — `sqn: null`,
  как и при нехватке N. Тест обязан покрыть это явно, не полагаться на то, что «само не
  случится».
