# Virex Trader: Grill / Discovery Notes
Дата: 2026-08-12 · Цель: вытащить из головы контекст по проекту virex-trader — зачем он, для кого, куда идёт, какие решения уже приняты и почему

## Summary / key decisions

**Что за продукт.** Virex — будущий SaaS для трейдеров: **сервис аналитики сделок, который показывает, на чём человек ошибается и что делает правильно.** Не журнал ради журнала и не терминал — диагностика поведения. Сейчас пользователь один (автор), первые полгода без подписки, с начала — QR на поддержку разработчика.

**Кому он нужен.** Не «трейдерам», а **трейдерам, которые хотят строить систему своих сетапов**. Автор сам назвал это главным риском: разметку тегами не бросит только тот, кто этого хочет. Для остальных половина продукта останется немой — это границы аудитории, а не дефект. Ответ продукта на риск: **«система его будет учить»** — мини-обучение плюс мини-курс «как построить систему с помощью сервиса», где курс работает воронкой, превращая «я сливаю» в «хочу систему».

**Три ошибки, которые ловит продукт** (формулировки автора): вход не по системе; слив депозита; долгое держание убыточной сделки.

**Как устроено разделение труда.** Граница проходит по типу правила:
- **качественное** («почему вошёл») → **теги**, которые пользователь создаёт сам, сколько хочет, свободной таксономией;
- **числовое и проверяемое** («сколько рисковал») → **декларация + автопроверка** на новом экране «Моя система».

Обе половины живут на одном экране — так «вход не по системе» перестаёт быть абстракцией.

**Ключевые решения по механике:**
- **PnL по тегам не делится** — сделка целиком засчитывается каждому своему тегу. Уже так и реализовано (`trades.service.ts:340`). Незакрытое следствие: в UI нужна подпись, что строки пересекаются и колонка не суммируется в общий PnL.
- **Таймфрейм — отдельное поле с фиксированным списком**, не тег (иначе «1ч»/«H1»/«час» разнесут срез). Значение поля — **то, на что трейдер ориентировался при входе**, а не длительность удержания. Заполняется руками, необязательно, со счётчиком незаполненных. Расхождение заявленного таймфрейма и фактического времени в позиции **и есть детектор ошибки №3**.
- **Правила «Моей системы»**: риск на сделку %, максимальная просадка за день %, максимум сделок в день, минимальный R:R (под вопросом — цели в данных биржи нет). Риск проверяется **по факту убытка**, а не по планируемому стопу.
- **Автоподсказки тегов** — сервис предлагает теги, пользователь подтверждает одним нажатием: «разметка должна стоить секунду, а не минуту».
- **Ключи только read-only, проверяется программно** — сейчас такой проверки нет вовсе. Утечка тогда означает раскрытую историю сделок, а не слитый депозит.

**Что технически блокирует продукт:**
- **Нет истории баланса.** Решение: модель `BalanceSnapshot (userId, exchange, at, equity)` вперёд + импорт депозитов/выводов для восстановления прошлого. Без переводов восстановление врёт именно там, где важнее всего: пополняют счёт обычно после убытка.
- **Фандинг не учитывается** (намеренно отброшен при импорте, иначе ломает реконструкцию позиции). Занижает цену ровно той ошибки, которую продукт берётся показать — долгого держания.
- **Шесть адаптеров из семи не видели живых сделок.** Проверен только Bybit.

**Сроки и готовность.** Два разных события: **приватный показ** паре знакомых трейдеров (ориентир — октябрь 2026, может быть раньше) и **публичный выход** — только когда готова вся система. Минимум до показа: мини-обучение, первый экран до подключения, «Моя система». Готовность определяется **не списком фич, а проходом пути**: человек с ключами Bybit регистрируется → подключает → видит сделки → ставит первый тег → читает первый срез, **ни разу не спросив автора**. Проверяется автором с чистого аккаунта.

**Ограничитель.** Автор один в проекте, время вкладывает нерегулярно. Октябрь ничем, кроме желания, не обеспечен.

**Вне рамок сессии.** Раздел «Боты» (DCA-grid) выведен за скобки: ветка `feat/dca-grid-bot`, страница в разработке, выход не гарантирован. Поэтому политика read-only принимается без исключений.

- Captured: **это будущий SaaS, а не личный инструмент навсегда.** Дословно: «я 1 пользователь пока, первые пол года в проекте не будет подписки. Я хочу сделать из этого сервис аналитики сделок пользователей что бы они понимали на чем делают ошибки а где правилньо торгуют».

### Q3 — что именно сервис называет ошибкой
- Asked: какие конкретно ошибки он ловит и как формулирует вывод пользователю?
- Captured: три ошибки, названные автором (в его формулировках):
  1. **«Вход не по системе»** — сделка открыта вне собственных правил.
  2. **«Слив депозита»** — потеря депозита; риск на счёт в целом, а не на одну сделку.
  3. **«Долгое держание сделки убыточной»** — убыток держат вместо того, чтобы резать.
  Форма вывода: **«цифры графики аналитика по каждой сделки с винрейтом общим за какой либо период»** — то есть подача через метрики и графики, посделочный разбор + сводный винрейт за выбранный период. Прямых текстовых вердиктов («ты теряешь X на отыгрыше») автор не просил.
- Замечание для дизайна: ошибка №1 требует, чтобы система знала *правила пользователя*; №2 и №3 считаются из данных сделок без внешнего знания.
- Flags: —

### Q4 — откуда сервис знает «систему» пользователя
- Asked: чтобы поймать «вход не по системе», нужно знать систему. Откуда она берётся? (моя рекомендация была — декларативная анкета правил на онбординге, теги вторичны)
- Captured: **рекомендация отклонена — механизм именно теги, размечает пользователь.** Дословно: «Есть большая аналитика по его сделкам времени pnl но пользователь сам создаёт и ставит теги на каждую сделку чтобы понимать почему он в нёё вошел».
  - Разделение труда в продукте: **сервис считает автоматически** — время, PnL, «большая аналитика» по сделкам; **пользователь даёт смысл** — сам создаёт теги (таксономия не навязана сверху) и вешает на каждую сделку, фиксируя *причину входа*.
  - Анкеты правил на онбординге нет. Ответ на «вход не по системе» рождается из пересечения тегов с цифрами, а не из декларации правил.
  - **УТОЧНЕНО в Q11: отказ от деклараций касается только «системы входа», не риска.** Числовое правило «риск на сделку в %» пользователь как раз объявляет сам, и система проверяет его автоматически. То есть граница проходит не по «декларации vs теги», а по **типу правила**: качественное (почему вошёл) — теги; числовое и проверяемое (сколько рисковал) — декларация + автопроверка.
- Flags: разметка руками — обязательный ручной шаг на каждой сделке; риск, что пользователь бросит размечать, и тогда половина продукта немая -> решение за автором, отдельно не обсуждалось

### Q6 — атрибуция PnL при нескольких тегах на сделке
- Asked: как считать деньги по тегу, если у сделки их несколько?

Обязательное следствие, которое автор принял как часть решения: **в интерфейсе должна быть явная подпись, что строки пересекаются и колонка не суммируется в общий PnL** — «иначе первый же пользователь решит, что у него сломана математика». Плюс нужен **срез «тег × тег»**: «мои пробои с тегом "нервничал" — они вообще в плюс?».
- **Проверено по коду (не спрашивалось):**
  - `TradesService.statsByTag` (`backend/src/trades/trades.service.ts:340`) уже считает именно так: сделка попадает целиком в бакет каждого своего тега (цикл `targets` на строках 386–401). Решение Q6 = то, что в коде, менять бэкенд не нужно.
  - Помимо винрейта бакет уже несёт `avgWin` / `avgLoss` / `profitFactor`, сплит long/short и спарклайн накопленного PnL — «сетап с винрейтом 40% всё ещё может быть лучшим».
  - Сделки без тегов идут в бакет `untagged`.
  - Срез «тег × тег» **уже существует**: `GET /api/trades/stats-by-tag-combo` (винрейт/PnL по точной комбинации тегов), подключён на фронте в `frontend/src/entities/tag/api/combo-hooks.ts:18`. Есть и модель `SavedTagCombo` — сохранённые комбинации.
  - Есть `statsByTime` с фильтром по `tagId` и «Лаборатория» (`GET /api/trades/lab`) — произвольные фильтры → сводка, фасеты, кривая PnL.

  - Оговорка в комментарии к `statsByTag` — «Trades without tags land in the untagged bucket so the numbers always add up to the overall stats» — верна только при ≤1 теге на сделку. При нескольких тегах сумма по бакетам заведомо больше общего PnL, что и есть причина требовать подпись.

### Q7 — таймфреймы
- Asked: чем должен быть таймфрейм — ещё одной категорией тегов, отдельным полем сделки или производной от времени в позиции?

  - Ценность среза: «на M5 у тебя −340$ и 31% винрейта, на H4 +900$ и 58%» — это **ошибка №1 («вход не по системе») в другой проекции: человек торгует не на своём таймфрейме.**

### Q8 — как таймфрейм попадает в сделку
- Asked: руками при разметке или автоматически из времени в позиции; обязательное поле или нет?
- Captured: **«Руками и со вторым согласен»** — заполняется вручную из выпадающего списка; поле **необязательное**, но с видимым счётчиком незаполненных («12 сделок без таймфрейма»), чтобы раздражало и заполнялось. Бакет «не указан» — по аналогии с `untagged`.
  - Принятое обоснование против автовывода из времени удержания: время в позиции — это **результат, а не замысел**. H4-сделку выбило стопом за 4 минуты → автомат запишет её в скальп и статистика соврёт именно на быстрых убытках.
  - **Определение таймфрейма от автора (дословно): «Это то на что ориентируется трейдер что бы открыть сделку».** То есть это таймфрейм *анализа/решения* — график, на котором принято решение о входе, — а не длительность удержания и не таймфрейм исполнения. Это снимает любую двусмысленность в UI: подпись поля должна спрашивать «на чём принимал решение», а не «как долго держал».
  - **Важное следствие для ошибки №3**: «долгое держание убыточной» детектится как **расхождение между заявленным таймфреймом и фактическим временем в позиции** (заявил M5 — сидел двое суток). Если таймфрейм выводить из времени, расхождение схлопывается в ноль и ошибка №3 перестаёт детектиться в принципе. Это связывает Q7–Q8 с ядром продукта, а не просто добавляет поле.

### Q9 — ошибка №2 «слив депозита»
- Asked: как сервис ловит слив депозита и что показывает пользователю?
- Captured: **приняты три метрики, все считаются из данных сделок без разметки** (автор подтвердил формулировку дословно). Продукт ловит не сам слив, а дорогу к нему.
  1. **Риск на сделку в % от депозита** — не среднее, а **распределение и хвост**: «в 8 сделках из 120 ты рисковал больше 15% счёта». Обоснование: «сливают не средним риском, а хвостом».
  2. **Эскалация после убытков** — объём следующей сделки после серии минусов, то есть отыгрыш: «после двух убытков подряд твой средний объём растёт в 2.3 раза, а винрейт таких сделок — 28%».
  3. **Просадка счёта** — кривая эквити, максимальная просадка, время восстановления.
- **Проверено по коду (не спрашивалось): в схеме Prisma нет модели баланса.** Модели: `User`, `ExchangeConnection`, `Trade`, `Execution`, `Tag`, `TradeTag`, `TradeContext`, `PositionTag`, `SavedTagCombo`, `DismissedTagCombo`, `OpenPositionSeen`, `DailyPrice`, `HourlyPrice`, `RefreshToken`. Поиск по `balance` / `equity` / `deposit` — пусто.
  - Значит **метрика №1 сейчас не вычислима в принципе**: «риск в % от депозита» требует знать размер депозита *на момент входа*, а история баланса нигде не хранится.
  - Метрика №3 частично вычислима: кривую эквити можно собрать из накопленного PnL, но это относительная кривая; просадка **в процентах** и «время восстановления» без абсолютного баланса врут.
  - Метрика №2 (эскалация объёма) вычислима из имеющихся данных — ей баланс не нужен.
- Не отвечено: что автор вкладывает в «слив депозита» (разовая катастрофа или медленное стачивание) — принятие всех трёх метрик покрывает оба сценария; постфактум или предупреждения в момент -> вынесено в Q11
- Flags: —

### Q10 — откуда брать депозит на момент сделки
- Asked: как получить историю баланса — снапшоты вперёд, восстановление прошлого, или отказ от процентов?

### Q11 — база для «риска в % от депозита»
- Asked: процент от чего (equity биржи / всего счёта / объявленный депозит); риск — это фактический убыток или планируемый (стоп × объём)?

  - Механика: пользователь **объявляет свой риск на сделку в %** (это правило, которого он обязуется придерживаться). Система при закрытии по стопу считает **фактический убыток относительно депозита** и **сверяет с заявленным %**. Нарушение = превышение собственного лимита.

Возможные развязки: (а) два типа подключения — журнальное read-only по умолчанию и отдельное торговое, подключаемое явно и осознанно; (б) бот не идёт в публичный продукт и остаётся личным инструментом. Боты были выведены за рамки этого грила (Q1), но политика ключей — нет, поэтому решение нужно.

### Q22 — read-only политика против торговых прав бота
- Asked: два типа подключения (журнальное read-only + отдельное торговое) или бот не идёт в публичный продукт?
- Captured: **«Не факт что он выйдет, эта страница под разработкой.»**
  - **Противоречия нет: бот не считается частью выходящего продукта.** Раздел «Боты» — в разработке, его выход не гарантирован.

### Q23 — контрольный вопрос: что не затронули
- Asked: качество данных (комиссии, фандинг, частичные закрытия); судьба существующих разделов; один ли автор в проекте; сколько времени вкладывает?
- Captured: **«Вроде всё, комиссии считаются, фандинг вроде нет. Страницы остаются разделы. Я один в проекте. Время по разному»**.
  - **Комиссии учитываются** — подтверждено кодом: `Trade.openFee` и `Trade.closeFee` (`backend/prisma/schema.prisma:95-96`).
  - **Фандинг не учитывается — подтверждено кодом, и это сделано намеренно.** При импорте истории исполнений записи с `execType: "Funding"` отбрасываются, потому что они несут `qty` и ломают восстановление размера позиции (комментарий к модели `Execution`, `schema.prisma:129-135`). Причина техническая и правильная, но следствие продуктовое: **реальная стоимость сделки занижена на сумму фандинга.**
  - **Это бьёт ровно по ошибке №3.** «Долгое держание убыточной сделки» — тот самый сценарий, где фандинг накапливается сутками. Продукт, который берётся показать цену этой ошибки, сейчас показывает её без самой дорогой части. Отдельный счёт фандинга (не подмешивая его в реконструкцию позиции) закрыл бы дыру.
  - **Существующие разделы остаются** — «Обзор», «Аналитика», «Лаборатория», «Теги», «Настройки» не режутся и не переосмысляются. Новое (обучение, «Моя система») добавляется к ним.
  - **Автор один в проекте.** Все роли — продукт, бэкенд, фронт, дизайн, поддержка первых пользователей — на нём.
  - **Времени вкладывается «по-разному»** — стабильного бюджета часов нет. В сочетании с «один в проекте» это главный ограничитель сроков: октябрь из Q17 не обеспечен ничем, кроме желания.
- Flags: фандинг не участвует в PnL -> завести отдельный учёт, не ломая реконструкцию позиций
