# Virex Trader

## Что это за продукт

Сервис аналитики сделок для трейдеров: показывает, **на чём человек ошибается и что делает
правильно**. Не журнал ради журнала и не терминал — диагностика поведения.

Три ошибки, которые продукт берётся ловить: вход не по системе, слив депозита, долгое
держание убыточной сделки.

Целевой пользователь — не «трейдер», а **трейдер, который хочет строить систему своих
сетапов**. Половина ценности держится на ручной разметке тегами, и её не бросит только тот,
кто этого хочет. Отсюда принцип: **«система его будет учить»** — обучение это поведение
продукта, а не раздел справки.

Продуктовая рамка целиком, с обоснованиями и открытыми вопросами:
`docs/superpowers/notes/2026-08-12-virex-trader-grill.md`.

## Разделение труда в продукте

Граница проходит по **типу правила**, и это определяет, куда класть новую функциональность:

- **качественное** («почему вошёл») → **теги**. Пользователь создаёт их сам, сколько хочет,
  таксономия свободная. Навязывать сверху нельзя.
- **числовое и проверяемое** («сколько рисковал») → **декларация + автопроверка**. Пользователь
  объявляет правило, сервис сверяет по факту сделок.

## Стек и структура

- **backend** — NestJS + Prisma + PostgreSQL. Модули: `admin`, `analytics`, `auth`, `bots`,
  `bybit`, `credentials`, `exchanges`, `market-events`, `settings`, `tags`, `telegram`, `trades`.
- **frontend** — Next.js App Router + FSD.
- **Docker Compose**, `start.bat` / `stop.bat` для локального запуска.

### Фронтенд: правила, которые ломались на практике

- **Слой страниц FSD лежит в `frontend/src/views/`, не в `src/pages/`.** `src/pages/`
  трактуется как Pages Router и роняет `next build` требованием `export default`. Проверять
  фронт нужно `npx next build`, а не только `tsc` — dev-сервер, eslint и vitest при такой
  поломке зелёные.
- **Никакой сырой разметки для повторяющихся элементов.** Всё через `shared/ui`: `Button`,
  `Field` / `Input` / `Select`, `PageHead`, `SectionHead`, `Skeleton`, `EmptyState`, `Money`,
  `KeyValue`, `ErrorNote`, `Wrap`, `LedgerTable`, `Seg`, `Pagination`, `DialogActions`.
  Цвета — классами из `globals.css` (`.muted`, `.pos`, `.neg`, …), не инлайновым `style`.
- **`widgets/` — только для блоков, реально используемых на двух и более страницах.** Проверять
  грепом, а не «на глаз». Блок одной страницы живёт в `views/<page>/components/`.
- Графики — своё SVG, приём `u = W / boxW` для мобильной адаптивности.

## Решения, которые нельзя нарушать не обсудив

- **PnL по тегам не делится между тегами.** Сделка целиком засчитывается каждому своему тегу
  (`backend/src/trades/trades.service.ts`, `statsByTag`). Деление поровну обессмысливает число.
  Следствие: в UI обязана быть подпись, что строки пересекаются и колонка не суммируется в
  общий PnL.
- **Таймфрейм — отдельное поле сделки с фиксированным списком, не тег.** Тегом он расползётся
  на «1ч» / «H1» / «час». Значение поля — **то, на что трейдер ориентировался при входе**, а не
  длительность удержания и не таймфрейм исполнения.
- **API-ключи бирж — только read-only, с программной проверкой прав при подключении.** Утечка
  базы тогда означает раскрытую историю сделок, а не слитый депозит. Реализовано для Bybit:
  `BybitApiKeyService` читает `/v5/user/query-api`, и `settings.controller` отказывает ключу с
  правом торговли или вывода. Незнакомая группа прав считается торговой — проверка падает в
  строгую сторону. Остальные адаптеры не возвращают `permissions`: это «неизвестно», а не
  «безопасно», и там правило пока не действует.

## Состояние на 2026-08-12

- Реально проверен только **Bybit**. Адаптеры OKX, Bitget, KuCoin, Gate.io, Binance USDⓈ-M,
  MEXC написаны, но **не видели ни одной живой сделки** — их поведение неизвестно, а не «в
  порядке».
- **Фандинг учитывается отдельно от PnL.** Из реконструкции позиций он по-прежнему исключён —
  записи `execType: "Funding"` несут `qty` и сломали бы восстановление размера, — но больше не
  выбрасывается: `fetchFills` отдаёт его отдельным списком `funding`, а хранится он в модели
  `FundingFee`. К позиции привязывается по символу и окну времени и показывается в раскрытой
  строке журнала. В `Trade.closedPnl` фандинга нет и не будет — это число биржи, и подмешивать
  в него своё нельзя. Комиссии считаются (`Trade.openFee` / `Trade.closeFee`).
- **Нет истории баланса** — ни модели, ни поля. Поэтому «риск в % от депозита» сейчас
  невычислим в принципе.
- Раздел **«Боты»** (DCA-grid) — в ветке `feat/dca-grid-bot`, в разработке, выход в продукт не
  гарантирован. В `main` его нет.

## Аналитика пользователей для владельца

`backend/src/admin` — отдельный раздел, отвечающий на вопрос «пользуются сервисом или нет»:
`/api/admin/analytics/overview`, `/users`, `/users/:id`, `/retention`.

- **Право админа живёт в `ADMIN_EMAILS` (.env), а не колонкой в `users`.** Раздел показывает
  почты и поведение всех пользователей, и выдавать к нему доступ данными в БД нельзя. Пустой
  список закрывает раздел для всех, включая владельца, — закрыто по умолчанию.
- **Пишется минута активности, а не событие на запрос** (`UserActivityMinute`). Интерфейс
  опрашивает позиции каждые несколько секунд; строка на запрос дала бы десятки тысяч строк в
  день на человека ради данных, из которых берётся только «была ли минута активной».
  `UsageTrackerService` копит в памяти и сбрасывает пачкой только **завершённые** минуты —
  поэтому минута уходит в БД ровно один раз и счётчики по разделам не удваиваются.
- **Сессии не хранятся, а выводятся** — цепочка минут с паузой меньше 30 минут, сшивается
  оконной функцией в SQL (`admin/usage/usage-queries.ts`). Определение сессии — соглашение;
  сохранённые сессии стали бы враньём, которое уже не пересчитать. Второй реализации в JS нет
  намеренно.
- **«Время на сайте» — это время с открытым приложением, а не время человека за экраном.**
  Фоновая вкладка опрашивает API сама. Отделить одно от другого можно только заголовком
  `X-Client-Active`, который фронт пока **не шлёт**, поэтому `foregroundMinutes` отдаётся как
  `null` — «нет данных», а не ноль присутствия. Оговорки едут в поле `caveats` вместе с
  числами, а не лежат в документации: метрику присутствия слишком легко прочитать как
  «человек сидел и работал».
- Воронка в `overview` повторяет путь из раздела «Готовность» ниже: регистрация → ключи →
  сделки → первый тег → первый срез. Считается за всё время, а не за окно отчёта.

## Готовность

Готовность к новому пользователю определяется **не списком фич, а проходом пути**: человек с
ключами Bybit регистрируется → подключает ключи → видит свои сделки → ставит первый тег →
читает первый срез, **ни разу не спросив автора**. Список фич всегда можно дополнить ещё одним
пунктом, и «готово» не наступает никогда; путь либо проходится, либо ломается в конкретном
месте.
